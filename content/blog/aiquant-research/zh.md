定时退出（time-exit）策略约定在一个固定时刻退出，回放就要读取那个时刻对应的价格。用这根 bar 的 open，和等它结束后再用 close，是两个不同的策略。AIQuant 中一个 time-exit 候选的 v4 修正过这个问题，按冻结的退出时刻读取路径 bar 的 open。精确到时间戳的规则，也可能在一个价格字段上走样。

AIQuant 是我与 Codex 持续开发的个人量化研究项目。我负责提出研究要求、选择下一步和审查结果，Codex 帮我实现、查资料和排障。项目把行情存储、Agent 的研究工具和策略回放连在一起，供我检验想法。目前没有达到晋级要求的候选，实盘和订单接口都没有启用。

这类实验需要能重读的数据，也需要把研究判断落到可以检查的程序上。数据湖和 Agent 工具由此有了各自的工作。

## Agent 读摘要，代码处理行情

早期 A 股样例的链路很短：行情、中文新闻、词典情绪分数，加上动量规则，输出事件驱动回测。这个入口仍留在 README 里。它适合检查流程是否接通，但词典给出的情绪分数，不能当作 Codex 已经做了事件研究。

后来的 Brain 工作流把这两件事拆开。Python 先收集材料、生成研究请求和按主题分开的阅读包，Codex 查证事件，写结构化 CSV 和研究笔记，程序再把这些结果转换成因子并运行实验。阅读包包括品种背景、高优先级新闻、已有事件记忆和待回答问题；需要哪个题目，再打开对应文件。

Agent 因而不必把整份行情数据读进上下文。它读报告，必要时追到代码和原件；计算和大文件扫描留给脚本。这里的“记忆”就是可定位的文件，并没有额外的向量检索服务。

实际调用边界可以缩写为：

```text
prepare：收集材料、生成阅读包
    ↓
Codex：查证、解释、写事件 CSV / 研究笔记
    ↓
post_codex：读取结构化产物、转换因子、运行实验
    ↓
报告与人工复查
```

本地 MCP 将 prepare、post_codex、读摘要、读研究包和写研究文件注册为具体工具。工具名从注册表分派，不接受任意命令字符串。研究包读取也检查解析后的路径是否仍在包目录内。这个 MCP 没有订单写入工具；项目的交易写权限仍由另一层规则控制。

Skills 保存可重复的操作要求：数据与计算、策略冻结、执行回放和报告整理各有入口。它们告诉 Codex 什么时候读哪个工具说明、需要什么输入、检查什么结果。实际数值仍要回到报告，不能因为 Skill 里留着一句旧结论，就把它当作今天的状态。

程序边界也有未补齐的地方。当前 `BrainRunner` 的 post 阶段发现事件 CSV 缺失，会提示下一步并返回；外层只要没有子进程报错，仍可写出 `succeeded`。所以这个值只说明编排没有捕获命令失败，不能单独证明事件研究已经完成。以后改这层，我会把“等待 Agent 产物”做成明确状态，再检查 CSV 的字段和内容；不能只看文件存在。

## 秒级数据，按小时落盘

行情不断写入，本地适合保留近期热缓存。长期历史和大报告放在远端，计算节点通过挂载读取同一份存储。计算路径和存储路径虽然不同，底下是同一份数据，没必要在两者之间再复制一次。

热数据写入 CSV，远端转换成带 ZSTD 压缩的 Parquet。Parquet 把字段按列存储，研究只需要部分列时，可以选择相应列读取；ZSTD 负责压缩。目录按采样间隔、品种和年月分区，热数据的实际文件则以 UTC 小时为单位。

**文件身份跟着数据时间走。** 一个小时第一次转换、随下一小时一起重试，或源文件修正后重新转换，都应该指向同一个逻辑分片。否则同一段行情会因为输入批次不同，变成几份同时存在的文件。

当前实现用 provider、采样间隔、品种和小时起点构造身份。下面是实际写入器的节选：

```python
logical_hour_id = logical_hour.strftime("%Y%m%dT%H")
logical_digest = hashlib.sha256(
    (
        f"{self.provider}|features|{self.interval}|{self.symbol}|"
        f"hour={self.logical_hour_start_ms}"
    ).encode("utf-8")
).hexdigest()[:20]
output_path = self.partition_dir / f"part-hot-hour-{logical_hour_id}-{logical_digest}.parquet"
self.temp_path.replace(output_path)
```

同一小时因此有稳定的目标路径，catalog 也使用同一逻辑键。重试替换这个分片，下一个小时有自己的文件。这个安排减少了重复输入带来的歧义；它没有把文件发布和 catalog 更新变成跨文件事务，中断恢复仍需要检查两边。

源 CSV 交错存着多个品种，转换时先分组暂存，每个分组缓冲达到阈值就写入计算节点的临时 spool。扫描完后再逐个发布到共享存储，同时只打开一个最终 Parquet 写入器。这样不用在网络文件系统上同时维持大量写入器，代价是多一轮本地临时读写。当前每组缓冲阈值为 2,000 行，总缓冲还会随活跃分组数增长；它是实现参数，没有吞吐对照测试支持“最优”。读写采用 PyArrow，行情来源是交易所公开数据；这里的工作是组织输入身份、同步和研究读取链路。

2026-10-09 17:24 的一份实际增量报告记录了：读取一份源文件，发布 94 个品种小时分片，共 332,575 行；观察到的最终 Parquet 写入器峰值为 1。这个数字只描述该批转换，不代表完整历史覆盖或所有时间段的质量。

## 同步确认要认出文件的版本

热文件在一小时结束前还会变化。假如转换程序处理的是旧内容，源文件随后又补了几行，单凭“这个路径处理过”就确认完成，会把新内容漏掉。

同步队列因此记录路径、大小、SHA-256 和观察时间。转换后 ACK 再比较源文件的大小和 SHA；不一致就输出 `maintenance_ack_blocked_source_changed`，等待新版本入队。旧的、只有路径的确认不够用。

本地清理对一秒 feature 文件使用同样的版本身份：超过保留期，而且当前内容匹配已确认的大小和 SHA，才进入可清理列表。这项保护的范围是 `features/1s`；其他热文件走各自的保留规则，不能概括成所有缓存都有相同保证。

增量目录索引也沿用变化清单，只更新受影响的文件记录。这里还有一项维护成本：这条增量路径不处理删除，需要完整重建来修复删除后的索引。文件数量再大，索引里的“存在”也仍然只是目录信息，不能替代逐行完整性检查。

## 数据粒度要跟着假设走

粗粒度筛选可以省计算，但前提是它保留了这个假设需要的信息。研究日级趋势和研究开盘后十秒的订单流，不能随手用同一种 bar 判断。

我在这个项目里提出过：依赖精细路径的策略可以直接进入精细回放，粗略步骤不必先算。原因很具体。如果信号来自一刻钟边界后的订单流，分钟 K 线已经把那几秒压在一起；如果同一根 bar 同时触到止损和止盈，只凭最高价和最低价也看不出谁先发生。一个不适用的代理回测，很容易把“数据表达不了这个问题”写成“策略没有用”。

现在的 L0–L7 更适合按证据依赖理解。L0 冻结策略定义；L1/L2 看历史与分段验证；L3 维护连续账户；L4 检查执行路径；L5 做成本与风险压力；L6 观察冻结后新数据；L7 才决定能不能晋级。前面的阶段不适用或只有部分证据，后面的研究可以继续，但必须说明缺什么，晋级条件不会随之消失。

## 退出时刻与价格字段要对齐

同一个策略名，不能保证不同回放在做同一件事。退出时间、价格字段、仓位容量和过滤规则都要固定，再由各阶段消费同一份定义。

time-exit v4 的一项修正，是在冻结的退出时间读取路径 bar 的 open。若策略要求在那个时刻退出，却用这根 bar 结束后的 close，价格就来自更晚的时刻，回放的策略已经改变了。把时间戳写得很精确，还不够；读取哪个价格字段同样重要。

早先 v3 还有一个账户语义问题：容量不足而拒绝新增仓位，曾被标成保证金耗尽。前者是容量规则挡住了新交易，后者则意味着账户风险事件。名字混在一起，风险报告会指向不同的问题。该版本现在只保留作诊断，没有拿修正后的数字替它追认旧结论。

这些问题也解释了为什么结果要绑定 profile 和 fingerprint。旧报告可以帮助找到错误或提出新假设，只有当前允许、内容身份匹配的证据才能控制当前状态。文件名叫 `latest`，或者某个数字很好看，都不能建立这种关系。

## 一个订单流信号的次月检查

项目还研究过 Kim 和 Hansen 的 [The Quarter-Hour Effect](https://arxiv.org/abs/2607.09426)。论文分析 Binance 永续合约在时钟边界附近的周期性交易，以及开盘订单不平衡与后续收益的关系。我这里讲的是 AIQuant 对其中一个信号的交易映射检查，范围比完整论文复现小。

规则使用一月确定的各品种订单不平衡绝对值 75% 分位阈值，按不平衡方向开仓，持有 12 小时。二月结果读取前已经冻结：每个品种同时只持一仓，持仓期间忽略新信号；入场取下一十秒完成区间的最后成交价，退出取 12 小时后的对应参考价，资金费按历史结算计入。这些是参考价格，还没有验证为真实可成交价格。

2024 年二月的检查得到 319 笔不重叠参考交易。固定 100 USDT 的合成账户，每个品种使用六分之一名义金额，不复利。改变假设的往返成本，结果如下：

| 假设往返成本 | 账户收益 | Profit factor | 最大回撤 |
| --- | ---: | ---: | ---: |
| 0 bp | +0.245% | 1.006 | 7.302% |
| 4 bp | −1.882% | 0.955 | 7.808% |
| 10 bp | −5.072% | 0.884 | 8.566% |

1 bp 是 0.01 个百分点，10 bp 即 0.1%。表里的成本是冻结场景假设，资金费已单独计入；它不是私人账户的实际费率，也没有覆盖点差、滑点、市场冲击或挂单不成交。Profit factor 是盈利交易利润与亏损交易损失绝对值之比，接近 1 就接近盈亏平衡。

零成本时也只有很薄的正结果，PF 约 1.006。因而不能说它原本是一个很好的策略，只是被 10 bp 费用压死了。一月确定的这条直接映射，没有在下一月保住足够的边际。

挂单费率较低，也不解决这里的成交问题。历史聚合成交能描述已发生的交易，却没有给出当时我的队列位置、部分成交或未成交。把费用设成零，只改变算术；它还没有回答这笔订单能不能做成。

这份二月结果标为 reused OOS：它位于已经发表论文的样本范围内，不能称作完全未接触的正式 OOS。它关闭了这条直接交易映射，不能据此否定论文在完整样本里的统计关系。看完结果再只留下表现最好的品种，也需要作为新假设重新冻结和验证。

## 下一步先补什么

现在最明确的成果是这套可以持续检查想法的研究工具。当前决策没有合格候选，缺失的执行证据和冻结后 clean OOS 仍然阻止晋级。

如果继续做这条订单流研究，我会先补可验证的成交模型，让参考价回放能够回答队列和未成交的问题。事件研究则要保留来源发布时间与可用时间，生成因子时不能提前用上后来才知道的消息。Brain 编排的等待状态也应补齐，免得下一次接手只看到了一个含义过宽的 `succeeded`。

我暂时不想用更多参数组合掩盖这些缺口。数据能不能准确重读，实验到底执行了哪个策略，失败发生在哪里，先把这几件事说明白，下一次尝试才有方向。
