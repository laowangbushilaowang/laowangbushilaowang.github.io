做 AIQuant 的起点很直接：我想让 Agent 帮我研究量化策略。收集新闻，理解事件，结合行情提出想法，再回测，看哪些值得继续。

接上自动化以后，我发现还有另一件事要管。行情在更新，网页也在刷新，研究却未必往前走：有时重新抓了一遍后台已经在收的数据，新闻分析和机会报告反而还是昨天的。到了下一轮，又从解释流程、修数据开始。

我花了不少时间约束的就是这些地方。**一次研究结束，要留下能让下一次接着做的结果：新假设、一次检验、明确关闭的方向，或者具体的数据缺口。** 只把同一套命令再跑一遍，我不满意。

这是我和 Codex 持续开发的个人项目。我提出需求、调整流程、审查结果，Codex 帮我写程序、查资料和排障。研究逐渐转向 AI、半导体主题合约，也用成熟加密合约检验方法。现在得到的是一套研究工具，尚没有符合晋级要求的策略，实盘与订单接口保持关闭。

## 先分清谁在做研究

早期流程能收集新闻、打情绪分数、运行回测。但关键词词典算出了一个正负分，不代表 Agent 理解了这条新闻。我在意的是：一篇技术论文、出口限制或公司合作，究竟通过什么渠道影响我关注的标的？需要查证的环节，还是得让 Codex 去读来源、解释关系。

另一方面，让模型逐行阅读行情又太浪费。我的安排是把调用时机、研究方法和实际计算分开：

| 部分 | 在这个项目里负责什么 |
| --- | --- |
| 自动化 | 按计划启动一轮工作，带上研究范围与任务要求 |
| Skills | 告诉 Codex 怎样查资料、衔接工具、检查结果，什么情况下应停下来 |
| Python / MCP 工具 | 采集与转换数据、运行实验、写报告，提供明确的调用入口 |

Skill 本身不会定时醒来；网页按钮也不会凭空叫出一个正在思考的 Codex。这几个入口可以配合，但不能混为一谈。

Brain 工作流把接口落在文件上：程序先准备材料，Codex 研究后写事件表和笔记，程序再读取这些产物生成因子与实验报告。本地 MCP 提供准备、读研究包、写研究产物、后处理等具体工具。

```text
程序准备材料 → Codex 查证与分析 → 结构化事件 → 因子 / 实验 → 报告
                    ↑                                      │
                    └──── 复查问题，决定下一轮查什么 ────────┘
```

模型不用一次吞下整个项目。研究包把相关材料分开，我先让它读摘要，再沿问题找文件：

```text
codex_research_pack/
├── 00_README.md               阅读入口
├── 01_today_summary.md        当天摘要
├── 02_symbol_profiles.csv     标的背景
├── 03_news_queue_high.csv     高优先级新闻
├── 05_macro_events.md         宏观事件
├── 06_company_events.md       公司事件
├── 07_science_events.md       科技与研究事件
├── 08_event_memory.md         已有分析
└── 09_questions_for_codex.md  还没回答的问题
```

这是实际研究包的目录节选。它用普通文件保存上下文，没有另起一套向量数据库。已有分析和待查问题分开放，下一次就能先看哪里还缺解释，而不是把所有新闻重新读一遍。

## Skills 要写清产物和失败以后怎么办

我最初也希望把事情尽量交给 Codex，尤其不满意新闻收集只靠固定脚本。后来留下来的分工更具体：可重复的收集、去重、时间检查交给程序；来源缺失、漏掉重要事件、需要判断行业关系时，再由 Codex 补查。

新闻这一项就值得单独写 Skill。我关注半导体合约，单搜公司名不够：政策、供应链、客户需求以及技术进展都可能有关。研究需要说明影响渠道，保留原始链接；论文里的实验突破，也要和真实产品、订单、商业化进度区分开。

采集还要能接着上一次做。已有 CSV 保留，按新闻 ID 和 URL 去重，增量补充，报告本轮新增、更新、跳过多少；最近时间窗内缺少哪些来源，也要说清。新闻够多和能够用于回测是两回事。回测需要知道消息在当时是否已经可见，后来补出的分析不能倒填成过去就知道的因子。

项目里的几个 Skill 因此承担不同任务：

| Skill | 我希望它固定下来的做法 |
| --- | --- |
| Brain | 准备研究包，读取上下文，写事件表和笔记，再做后处理 |
| 新闻研究 / 聚合 | 针对目标标的补来源、增量去重、检查发布时间与覆盖缺口 |
| 前沿研究 | 把论文、报告和开源方法改写成可检验假设，列出所需数据和第一项实验 |
| 策略全流程 | 固定策略定义，安排适用的验证，留下各阶段结果和未完成项 |
| 数据与计算 | 使用已有采集链，安排本地缓存、远端历史与计算任务 |

这里有个容易高估的地方：把要求写进 Skill，还需要检查程序有没有真的完成。现有 Brain 编排中，缺少事件 CSV 时可以只留下提示，外层仍返回 `succeeded`。所以我读报告时还得看事件产物和下一步，不能只认一个绿色状态。这一处也仍是编排需要补齐的地方。

## 行情持续采集，研究按需读取

后台已经在收行情，研究任务就不该每次再启动一套采集。我曾多次把 Codex 拉回这个分工：读已有数据，补新闻分析，更新由这些输入生成的报告。否则抓取做了两遍，真正要看的结果没变。

行情采集和网页后来分开：后台通过 WebSocket 接收数据，生成近期缓存和小型状态文件；网页读取这些产物。关掉一个浏览器标签，不应该等于关掉采集。网页每秒读取一次本地状态，也不等于每秒向交易所重新请求一轮数据。

存储按用途安排：

- **本地**放近期热缓存、当前状态和网页需要的小报告。
- **远端**保存长期历史与大报告，计算节点读取同一份共享存储。
- 历史特征按时间、标的分区，以 Parquet / ZSTD 保存；研究按窗口和字段读取。

这也和策略有关。日级趋势可以用较粗的 K 线；订单流、短时退出和止损先后，需要更细的路径。项目的秒级特征不等于毫秒级数据，今天采集正常也补不出过去没收过的盘口。

我的经验是先问清策略需要什么数据，再决定怎么筛。若信号来自时钟边界后十秒的订单不平衡，先压成分钟线，可能连要检验的现象都丢了。粗筛节省计算的前提，是这个代理还表达得了原问题；不适用时应记录原因，进入相应的精细检验。

## 一轮研究怎样接到下一轮

持续运行以后，另一个问题开始突出：历史回测、账户回放和影子观察，可能名字一样，底层却用了不同规则。我专门要求把它们统一。进出场、过滤条件、仓位、退出时间和成本假设，只要中途换过，就很难解释结果为什么不同。

现在我用一套冻结的策略定义贯穿各阶段。一次研究大致这样走：

1. **先找值得检验的假设。** 查已有结果和外部方法，避免把失败方向换个名字再做。
2. **固定输入和规则。** 声明数据窗口、策略版本与账户假设，再运行实验。
3. **从广到窄测试。** 对适合 K 线表达的策略先筛少量代表版本，留下有希望的再做分段、账户、执行与成本检查。
4. **解释失败发生在哪。** 缺输入、样本不足、成本后失效、不同阶段规则不一致，分别处理。
5. **留下下一步。** 关闭、等待补数据或登记新假设；改规则就成为新版本。

程序里把这些验证记为 L0–L7，但研究不必机械地每次从第一层重跑。重要的是知道这个候选缺哪一块，继续做哪项检验能回答问题。正式样本外数据也不能一边看、一边调参数，再继续叫“没见过的测试集”。

还有一项我反复纠正过：Agent 会读到旧流程的高收益，把它当成新流程的结果。项目因此保留唯一当前决策和允许参与当前判断的报告清单。历史材料仍可提供想法，但要重新按当前规则验证。文件名里写着 `latest`，解决不了这个问题。

## 网页要让我看懂实验到了哪里

我想通过网页知道：研究了什么、为什么看这个策略、数据有没有过期、还缺什么。只放一条收益曲线，看不出这些关系。

早期控制面可以启动已登记的研究任务、看日志和打开报告。后来的 Chart IQ 把策略雷达、看盘工作台等内容分成标签。下面是策略雷达的实际界面：价格接近报告触发位时，还要检查策略是否已经退化、验证结果是否允许继续参考。

![Chart IQ 策略雷达的退化提示](/images/aiquant/chart-iq-strategy.webp "2026 年 6 月 1 日的实际界面裁图，已去掉账户状态区域。红色提示说明该策略当时已退化，价格触发位不能直接当作进场建议；此图不代表当前市场状态。")

看盘工作台负责对照价格、图层和研究结果。行情更新与报告更新各走自己的节奏，网页同步报告时也要保留正在阅读的详情。我遇到过点开详情又被刷新弹回去的问题；这种小问题会直接打断复查。

后续代码还加入后台任务状态接口：显示状态时间、延迟和缺口；默认只能监视，只有已经接入受控管理器的任务才提供启停。它能帮助检查流程，但不是一个能任意控制所有研究任务的网页 Agent。

## 一次订单流研究，最后停在了成本这里

用一个实际例子看这套流程：[The Quarter-Hour Effect](https://arxiv.org/abs/2607.09426) 研究永续合约在时钟边界附近的交易现象。AIQuant 检查过其中一种交易映射：用一月订单不平衡绝对值的各品种 75% 分位阈值，沿不平衡方向入场，持有 12 小时，再看二月。

二月得到 319 笔不重叠参考交易。使用 100 USDT 合成账户，每个品种分配六分之一名义金额，不复利，历史资金费单独计入。改变假设往返成本，结果如下：

| 往返成本假设 | 账户收益 | Profit factor | 最大回撤 |
| --- | ---: | ---: | ---: |
| 0 bp | +0.245% | 1.006 | 7.302% |
| 4 bp | −1.882% | 0.955 | 7.808% |
| 10 bp | −5.072% | 0.884 | 8.566% |

1 bp 是 0.01 个百分点；Profit factor 是总盈利与总亏损绝对值之比。零成本时已经接近盈亏平衡，4 bp 后转负，这条直接映射不足以支持继续。看完结果再删掉亏损品种、加杠杆，会变成另一项需要重新验证的假设。

这仍是参考价诊断：入场取下一十秒完成区间的最后成交价，退出取 12 小时后的对应参考价，未验证真实成交、队列和滑点；二月又在已发表论文的样本内，属于重复使用的样本外窗口，不能当全新正式 OOS。它没有否定论文里的统计关系，只回答了这条交易映射是否值得继续。

AIQuant 目前还没有可晋级候选。它已经让我能把一次研究的来源、数据、规则和结果接起来，也把不少不成立的想法关掉。对我而言，下一轮最有用的输入是失败的具体原因：缺少成交数据，就去解决那个缺口；成本后优势消失，就换一个有依据的假设。这样才用得上 Agent 持续工作的时间。
