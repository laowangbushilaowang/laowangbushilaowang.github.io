在 iPhone 上看见远端登录页之后，我发现拖动还是很难用。手指已经往右走，屏幕里的控件却没及时跟过来；等画面更新，又不知道刚才那段移动到了哪里。

远端浏览器的触控，需要一个足够短的反馈闭环：发出坐标，页面响应，再把新画面送回来。只把点击传过去，或只让截图定时刷新，都不足以让人准确拖动。我这次做的私有 iPhone 管理端，正好把这个问题暴露得很具体。

它是本地工作台的移动入口，订单、任务进度和参数用 SwiftUI 原生页面显示。需要操作原网站时，才打开云端浏览器画面。我负责使用流程、交互要求和实际反馈，Codex 协助写代码、排查与检查。下面讲这条触控链路怎样工作，也讲一次没有支持“优化成功”的测速。

## 一次拖动，要等哪些东西

手机上的画面是远端 Chrome 的截图。拖动开始时，SwiftUI 读取手指位置；客户端通过 SSH 把操作交给固定的网关，网关再转给浏览器控制器。控制器用 Chrome DevTools Protocol 发出鼠标按下、移动或松开事件，然后截图，把 JPEG 数据传回手机。

一次移动因此包含输入传输、浏览器执行、截图编码、回传和本地显示。早期版本还为每次移动新建 SSH 连接，完成一个请求就关闭它。手指连续移动时，这条短请求路径被反复走了一遍。

我提出的要求是拖动过程中能看到反馈，不能等松手才给最终结果。后来的实现让交互页面持有一个已经认证的 SSH 连接和命令通道，按行发送 JSON 请求，按行读回应。离开页面后再关闭通道。手机 SSH 部分使用 Apple 的 [SwiftNIO SSH](https://github.com/apple/swift-nio-ssh)，项目实现的是自己的请求与生命周期管理。

这里的“持续通道”容易让人误会。它不是连续视频流：每次指针请求仍会等待一张截图，收到后才能继续处理下一次移动。复用省掉了反复建立连接和启动网关命令的工作，截图还在原来的位置等着。

## 复用连接之后，画面仍然慢

2026 年 10 月 9 日，真机诊断留下一组数据：

| 测量项 | 时间 |
| --- | ---: |
| 单次新连接路径取画面 | 1,011 ms |
| 打开持续浏览器连接及通道 | 96 ms |
| 在该连接上取一张画面 | 2,459 ms |

顺序是先取一次画面，再打开持续连接，再取一次画面。前两次读取诊断文件时浏览器还不可用，稍后才拿到上面这组完整结果。

更慢的那次恰好走了复用连接。这不能说明复用让它变慢，也不能把两行相减后宣布“提速了多少”：这是不同时间点各一次的读取，页面状态、服务端等待和网络条件没有被控制。

不过，它足以否定一个过于简单的解释——把所有卡顿都归给握手。96 毫秒是打开整条持续路径的时间，并非纯 SSH 握手分项；两次取帧又混合了截图、网关和传输的耗时。这里需要继续分段测量。手指在拖动时，不会因为后台用了一个更合理的连接对象，就体谅那两秒钟的空白。

当前截图代码先尝试 JPEG quality 52，数据过大时改用 34，并限制返回的 Base64 长度。它避免单张画面无限变大，但清晰度会下降，限大小也不等于限延迟。[CDP 的截图接口](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-captureScreenshot)只是这条路径中的一环。

## 手指已经往前走，旧坐标还在排队

如果把每个 `onChanged` 都存进队列，网络处理得越慢，积攒的旧位置越多。用户已经松手，服务端可能还在追赶中途经过的坐标。随后收到的画面，又属于更早的一次移动。

这个项目用 `pointerLatest` 保留最新位置。一个请求还没结束时，新手势回调只覆盖它，不再另建一项等待发送的任务。发送循环收到画面后，重新读取最新位置。

下面保留了实际 Swift 循环的主要分支，省略按下、错误处理和退出清理：

```swift
while true {
    let next = pointerLatest ?? last
    if abs(next.x - last.x) + abs(next.y - last.y) >= 2 {
        let moved = try await control.pointerMove(next)
        browserFrame = scenePhase == .active ? moved : nil
        last = next
        continue
    }
    if pointerFinished {
        let released = try await control.pointerUp(next)
        browserFrame = scenePhase == .active ? released : nil
        return
    }
    try await Task.sleep(for: .milliseconds(50))
}
```

相差不足两个浏览器坐标单位时，循环稍等；有足够移动，就发最新点。松手标记单独保存，最后仍发送释放事件。它合并的是移动位置，不是把按下和松开一起扔掉。

拖动普通控件时，避免播放一串过时位置很有用；如果要画一条笔迹，中间轨迹本身就是内容，不能沿用这套合并办法。即便只拖控件，一次跨度太大的跳跃是否可靠，也得在真实页面上测。

还有另一种遗留状态：手机锁屏或连接断开，服务器却一直认为鼠标按着。客户端离开交互页、失去活动状态时会标记手势结束；异常路径尝试补发松开。浏览器控制器也设了 20 秒的指针超时，尝试释放并清理状态。这是失联后的兜底，正常拖动不能靠它收尾。

画面空闲时的自动刷新和手势发送共用忙碌判断，拖动中不另发一轮定时取帧。这样减少了同一通道上两种用途相互排队的机会；每次移动仍然等待截图，所以还没解决反馈闭环里最慢的部分。

## 缩放以后，点在哪里

画面能传回来，还得点得准。手机显示的图片尺寸和浏览器坐标不是一回事。图片放大后，直接拿手指的屏幕坐标去点击远端，会越点越偏。

项目从图片上的局部手势位置做映射。假设远端截图宽度是 `frame.width`，实际显示宽度是 `displayWidth`，保持原比例缩放，则映射的主要计算是：

```swift
let scale = Double(frame.width) / Double(displayWidth)
let x = min(Double(frame.width), max(0, Double(location.x) * scale))
let y = min(Double(frame.height), max(0, Double(location.y) * scale))
```

这里的 `location` 属于图片上的手势层，不能随便换成整个屏幕的坐标。服务端若只截取远端页面的一块区域，还会在 x 坐标上加回该区域的 `viewOffset`，再用 [CDP 鼠标事件](https://chromedevtools.github.io/devtools-protocol/tot/Input/#method-dispatchMouseEvent)发给 Chrome。

放大后还会遇到手势冲突：一根手指到底是在平移图片，还是拖动远端页面？我保留了明确的“移动画面／操作”切换。移动画面时，触控覆盖层不接收远端操作，让 ScrollView 负责定位；切回操作后，手势才传到网页。多一个按钮有些笨，但它至少让这次拖动的目标清楚。

普通输入也不必跟远端像素较劲。登录资料改用原生表单，输入完成后交给当前页面的固定字段；需要本人完成的验证仍留在原网站。下面是开发时留存的模拟器截图。

## 离开画面，留住登录

触控通道跟着手机页面走，远端浏览器却不能照着同一套规则关闭。

点击“完成”只是离开画面，关闭不再需要的手机交互连接；服务器上的任务可能还在运行。释放内存则会结束远端浏览器进程，把资源让出来。退出登录又是另一个动作，需要处理认证状态。早期把这些事情混在一起，浏览器控制器重启后，临时环境里的登录就丢了。

后来的版本把浏览器 profile 放到持久目录中。`parked` 表示进程已停，profile 还在；重新启动时使用原 profile。它保留重新打开所需的本地状态，网站仍可能让会话过期，不能据此承诺永远不用登录。

小服务器还得决定哪个浏览器占内存。代码允许保留一个空闲的已登录浏览器，但会检查可用内存；另一种需要浏览器的任务启动前，先停放前一个，再检查启动余量。手机回到首页，不等于应该删掉登录。反过来，保存了登录，也不等于应该让 Chrome 一直抢着内存。

状态读取用 `closed`、`parked`、`login_required`、`verification_required`、`ready` 和 `unknown` 决定界面的下一步。`ready` 只说明预期列表页可见，不能替后续任务宣布成功。

## 真机上看到什么，模拟器上看到什么

这个项目里，版本混淆曾经直接打断验收。我遇到过“新功能已经安装”的反馈与手机上看不到入口相冲突，后来又明确要求用模拟器继续调试，让自己的手机保持可用。编译通过、某台设备安装完成、页面真正可操作，需要分别确认。

早期手机版本已经通过设备密钥读取过订单，我也在真机上看到了远端登录页，报告了难以点击和拖动的问题。上面的取帧数据来自真机诊断。到本文核对的 10 月 9 日记录，1.6 版已经在模拟器中更新，实体手机仍是此前的版本；不能把模拟器的新布局当成手机已升级。

本次写文章时，复查了 7 项网关测试和一份浏览器状态测试：请求参数边界、普通列表不返回私密内容、连续 JSON 行读取、在系统 Python 下不误导入门户依赖等检查通过。它们使用临时数据和模拟页面，不测真机触控手感。此前模拟器的构建记录也只证明那次构建完成。

下一步我会先拆开输入确认和取帧：让坐标尽快到达页面，再控制截图的更新频率，同时让显示的画面能对应到已处理的输入。随后在同一页面、同一设备上重复测冷连接和复用连接，把服务端截图、传输和手机显示分开记时间。这还是改进方向，现有实现没有完成这套比较。

下一次验收就用同一个控件：拖动过程中能看清位置，松手后不再追赶旧坐标，断线重进不会留下一个按着的鼠标。
