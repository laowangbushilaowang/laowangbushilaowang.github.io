给工作台加上 iPhone 管理端，是因为我想把原来依赖自己电脑的操作搬到服务器上，再用手机查看订单、处理任务。那台服务器只有 2GB 内存，我一开始就担心几个浏览器同时开着会撑不住。

后来问题真的出在这里：连查询会员信息，也会报内存不足。手机能连上、按钮能点，离顺手使用还差不少。我又追问了一串问题：到底是谁在占内存？普通查询为什么也需要完整网页？慢一点没关系，能不能用硬盘 Swap？

这篇讲我怎样把这些问题拆开处理。需求、界面安排和使用反馈由我提出，Codex 协助实现与检查；原生端用 SwiftUI，SSH 部分基于 Apple 的 [SwiftNIO SSH](https://github.com/apple/swift-nio-ssh)。

## 手机上管理任务，服务器上执行任务

我需要的移动端，可以查订单、看账号信息、改参数，也能查看执行进度。只有必须操作原网站时，才进入远端浏览器。

早期界面把许多功能收进“选择参数并一键开始”，用起来却缺东西。一次只想查信息，或者任务结束后要归档，都不该被迫重新走完整流程。我要求按实际使用顺序拆开：账号与会话、资料与参数、执行、后续处理、订单管理。常用操作直接露出来，较少用的内容折叠。

手机和 Mac 工作台调用同一套云端任务队列。任务交给服务器以后，离开手机页面不会结束它；重新打开时，读取原任务的状态。连接中断、没收到返回时，也要找回原来的请求，避免又创建一份。

```text
iPhone / Mac：选择任务、提交、查看进度
                       ↓
服务器：保存任务 → 排队 → 执行 → 保存结果
                       ↓
需要人工操作原网站时，手机接入已有浏览器窗口
```

*控制与执行的职责概览。手机页面和服务器任务有各自的生命周期。*

这样，手机主要负责告诉我发生了什么、让我决定下一步。持续运行的工作留在服务器上。

## 先减少需要浏览器的地方

碰到内存不足，我最先追问的是压缩和 Swap。但在应用里，还有一件更直接的事：少启动一个完整浏览器。

查询一份账号状态，只需要拿到结果。早期实现里，这类操作也可能先启动浏览器、加载完整首页，再从页面里请求数据。首页上的聊天界面、脚本和渲染状态，都跟这次查询一起占着内存。

后来的实现逐渐分成两条路径：

- **普通查询和管理操作**复用本地工作台已有的 HTTPS 模块，返回结构化结果，显示在原生页面里。
- **登录、会话恢复或需要本人操作网页的情况**，接入对应账号的浏览器窗口。

中间也尝试过轻量页面：保留原账号的浏览器上下文，查询完成后释放完整首页的渲染负担。这个办法适合仍然需要浏览器上下文的路径；普通查询能直接调用接口时，就不用为它再开 Chrome。

这项改动比单纯降低截图质量更接近内存问题本身。截图变小，主要减少的是画面编码和传输量，原来那个完整浏览器仍然在服务器上。

## 让几个重任务轮着用内存

仍然需要浏览器的部分，也不能同时随便开。

云端 worker 按队列串行处理任务。开始另一类重操作前，先停放暂时不用的浏览器，再检查可用内存。这里的“停放”会结束进程，但保留浏览器 profile，也就是下次启动要用的本地浏览器资料。

保留登录资料和让进程常驻，是可以分开的。这样不用每次都从零准备浏览器，也不用为了留住登录就让它一直占着内存。网站仍然可能要求重新登录，profile 不能保证会话永不过期。

几项资源约束放在服务配置和启动逻辑中：

| 对象 | 配置或规则 | 用途 |
|---|---|---|
| 常驻浏览器服务 | 内存硬上限 600 MiB | 限制这一组浏览器进程的占用 |
| 云端任务 worker | 内存硬上限 900 MiB | 给其他服务留出空间 |
| 新的付款任务浏览器 | 停放前一个后，要求至少 1,000 MiB 可用内存 | 给冷启动留余量；复用已有窗口另走检查 |

*这些是实现中的配置与启动条件，不是各进程的占用实测。*

手机上也加了窗口管理：看哪些窗口还留着、哪项任务正在占用，必要时接管原窗口，或关闭它释放资源。我明确要求过这些入口，因为只看到“内存不足”，却不知道能关什么，最后还是得回电脑处理。

离开画面、停放浏览器、退出登录分别做。任务还在运行时，不能因为手机关了一个视图，就顺手把服务器上的窗口一起杀掉。

## Swap 也试过，但有一条路线后来撤回了

我当时的想法很朴素：速度比内存慢一些可以接受，硬盘总还有空间。

这里要分清磁盘 Swap 和 zswap。磁盘 Swap 把暂时不用的内存页放到磁盘上，代价是之后访问时的 I/O。zswap 则先把页面压缩在内存里，减少一部分磁盘读写；它自己也要用 RAM 和 CPU。[Linux 的 zswap 文档](https://docs.kernel.org/admin-guide/mm/zswap.html)解释了这层缓存的关系。

所以，“做压缩为什么还占内存”并不矛盾。压缩能否划算，要看腾出的空间和压缩池自身的成本；频繁访问的数据不断换进换出，交互还可能更慢。

项目里曾加入一个加密磁盘分页原型：普通文件经过 loop 设备和 dm-crypt，再作为 Swap，并配合 zswap。后来检查这条存储路径时，发现它在内存回收中有死锁风险：需要把页面换出去才能腾内存，但写到底层文件系统又可能要先分配内存。

这条链路的风险，在 [Linux Block 邮件讨论](https://www.spinics.net/lists/linux-block/msg133309.html)里有明确解释。它针对的是文件之上再叠 loop 和加密的方式，普通直接 Swap 文件不能一概而论。项目随后撤回了这套原型的启用逻辑，保留状态检查和有条件的停止恢复。我没有把它当作一个成功的扩容结果。

另外，worker 配置里的 `MemorySwapMax=2G` 只是允许使用的上限，不会凭空创建一块 Swap。磁盘空间、实际启用的交换设备和进程额度，是不同的东西；[cgroup 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)也分别记录内存与交换空间。

这次尝试以后，我优先保留了减少浏览器、串行执行、复用窗口和启动前检查这些应用层改动。分页可以帮助缓解压力，具体后备存储仍得单独核对，不能把 2GB RAM 加几 GB Swap 直接当作同等速度的内存。

## 远端画面留给需要它的操作

普通表单用原生控件，远端浏览器负责原网站上的交互。下面是开发早期留下的原生登录表单。

![iPhone 管理端的原生登录表单](/images/projects/private-iphone-workbench/native-login-form.webp)

*1.0 版的实际模拟器截图，使用测试邮箱与示例密码；已裁切压缩。它展示表单布局，不代表登录成功，也不是当前源码版本的界面。*

远端画面走的是“发送操作、获取截图、显示”的循环。手指拖动时，我遇到过画面跟不上、对不准的问题。后来复用 SSH 通道，并只保留尚未发送的最新移动位置；松手事件单独保留，避免服务器还在追赶一串旧坐标。放大图片后，点击也要按图片局部坐标换算回浏览器坐标。

这些改动没有消除截图成本。一次真机诊断中，两条路径取帧分别用了 1,011 ms 和 2,459 ms，各测一次，不能拿来证明提速。持续画线一类依赖中间轨迹的操作，也不适合简单丢掉中途坐标。

原生界面同样需要实际点进去验收。我还遇到过订单列表能显示、点进详情却闪退；只确认接口返回 JSON 看不到这个问题。源码后来给分页视图增加了类型组合边界，但构建通过、模拟器能打开和自己手机上能用，仍要分别检查。

这套 App 的用途，是让我在手机上找到一项任务、看懂进度，并管理它占用的窗口。当前源码已经有这些分工和资源规则，真机拖动的流畅度、长时间运行和完整业务流程还需要各自验收。
