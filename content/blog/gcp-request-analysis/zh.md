2023 年的云计算课程里，我做了一组连续作业：先让服务器从云存储里返回文件，再记录请求、写入数据库，最后把积累的数据拿去训练模型。每次作业都在上一版上添一点，最后串成了一条从 HTTP 请求到模型评估的流程。

其中有两项结果很有意思。用 IP 预测国家，随机森林得到了 **100%**；用国家、性别和年龄预测收入，分类器只有 **12% 左右**。同一批数据，差距这么大，原因得回到最开始的请求生成程序里找。

这是一组课程实验。请求客户端由课程提供，我完成服务端接入、数据库和模型部分；其中的数据都是模拟请求属性，不能当成真实用户画像。

## 先把文件服务接起来

最初的服务做的事很简单：接收一个路径，到 Cloud Storage 找对应的 HTML 文件，再把内容返回给客户端。我用 Flask 处理路由，存储客户端负责读取对象。文件放在存储桶里，Web 服务本身不用保存一份副本。

后续作业逐渐加入了请求方法检查、按请求头判断的规则，以及消息和日志。整个流程可以这样看：

```text
课程提供的 HTTP 客户端
       │  文件路径 + 模拟请求属性
       ▼
Flask 服务 ──读取文件──► Cloud Storage
       │
       ├─ 运行信息 ──► Cloud Logging
       ├─ 规则事件 ──► Pub/Sub ──► 订阅程序
       └─ 请求记录 ──► Cloud SQL ──► 模型分析
```

这几个出口各有用途。Logging 留下运行和错误信息；Pub/Sub 让另一个订阅程序接收事件；SQL 则把每次请求变成可以按字段查询的数据。订阅程序的工作也很直接：打印收到的消息，再确认接收。它和返回文件的请求路径分开运行。

接起来以后，需要验证的不只是浏览器能不能显示文件。文件不存在时有没有相应记录？请求没带齐属性怎么办？这些问题决定了后面拿到的表到底表示什么。

## 给请求设计一套表

数据库作业要求至少符合第二范式。我把国家规则、成功请求和失败请求分别保存，主要关系如下：

```text
Country
  country_name  主键
  is_banned     该国家对应的课程规则
       │
       └── Request.country_name  外键

Request
  request_id    主键
  country_name, client_ip, gender, age, income
  time_of_day, requested_file

Request_fail
  request_id    主键
  time_of_day, requested_file, fail_code
```

国家对应的规则只在 `Country` 里维护，请求表通过外键引用它。否则同一国家出现多少次，规则就得跟着复制多少次，改一次规则还要改一批请求记录。

这里的分表解决的是重复和依赖关系。给每张表加一个自增主键，并不能代替检查字段之间的依赖，也不能自动证明整套设计没有问题。

失败记录只保存时间、文件和错误码。下面两条 404 就能让人看到哪些文件请求失败了：

![失败请求表中的两条 404 记录](/images/cloud-requests/failed-requests.webp)

*实际课程运行中的表内容，裁去了无关界面。这两条是模拟文件请求的失败记录。*

这个结构适合按错误码检查失败，但如果还想按国家统计失败请求，就得把相应字段也留下。成功表有国家，并不能补出失败表里没记录的国家。采集时少存一个字段，分析时往往就少了一种问法。

服务里还做过缺字段时填默认值的处理。这能让一次简单请求继续入库，但默认国家、默认 IP 与客户端实际提供的属性，含义不同；如果不区分，模型就会把程序补的值也当成观测。

## 两个模型，学到的是两种不同的数据关系

有了请求表，我把数据读成 DataFrame，再准备两个分类任务。代码使用 80/20 的随机切分；这批运行数据有 100,000 行，结果如下：

| 任务与代码 | 准确率 |
|---|---|
| IP → 国家，Random Forest | 100.00% |
| 收入分类，保存版本为 SVC | 12.23%、12.60% |

这里的百分比都是课程模拟数据上的结果。它们没有回答真实 IP 地理定位或真实收入预测能做到什么程度。

先看第一个任务。客户端会为每个国家分配一组互不重复的 IP 前缀，生成请求时先选国家，再从这个国家的前缀中生成 IP。因此，同一次数据生成过程里，**IP 前缀和国家之间存在固定映射**。

随机按行划分训练集和测试集后，同一前缀生成的请求可能同时出现在两边。随机森林只要学会这套有限的映射，就可以在测试集上做得很好。

![国家分类输出中的 100% 准确率](/images/cloud-requests/country-result.webp)

*国家分类的实际输出。100% 对应这套模拟前缀映射和按行随机切分，不代表能识别没见过的新前缀。*

第二个任务的生成方式完全不同。客户端中的逻辑，缩写后大致是：

```python
country = select_country()
ip = make_ip(select_cidr(country))

gender = get_list_item(gender_levels)
age = get_list_item(age_levels)
income = get_list_item(income_levels)
```

*这是生成逻辑的简写，省略了请求组装；后面三项分别随机抽取。*

收入有 8 个类别，每个请求都独立随机选一个，和国家、性别、年龄没有预先设置的关系。只拿这些输入，平均猜中的概率就是约 `1 / 8 = 12.5%`。两次输出的 12.23% 和 12.60%，正好在这个水平附近。

![收入分类输出中的数据形状和 12.60% 准确率](/images/cloud-requests/income-result.webp)

*收入分类的一次实际输出；另一条结果为 12.23%。这两项没有被当作同条件下的算法改进对照。*

这时继续换一个更复杂的模型，不能凭空增加输入与标签之间的关系。第一个任务容易，是因为生成器已经放进了可学习的映射；第二个任务困难，是因为目标值本来就是独立抽的。看到高分或低分，都得先知道数据是怎么来的。

回看代码，数据生命周期还有一处需要拆开：建表初始化和查询放在了同一个模块，导入时会执行重建表。模型脚本应该只读已经采集的数据，不应该顺带触发初始化。这个课程版本的代码和当时的运行环境仍有差异，不能直接把当前仓库当成一键复现实验。

这组作业把存储、消息、数据库和模型接在了一起，也让我把模型结果往前追到了请求生成方式。服务能够写出一张表以后，还要弄清每个字段代表什么、哪些关系是真实存在的，才知道下一步该问数据什么问题。
