一篇论文里写着数据编号，顺着编号下载，磁盘上多了一批文件。接下来，分析能开始了吗？

还差不少。哪个文件是表达矩阵，哪个只是样本说明？几个矩阵属于不同样本，还是同一个样本的不同部分？文件名里的编号，怎样对应到论文里的组织、年龄和处理条件？这些关系没有理清，代码可以正常读出一个矩阵，但我们未必知道自己读了什么。

我在广州国家实验室做 BioFlow，是想把公开多组学数据整理起来，服务虚拟细胞模型的数据语料库建设。这里的重复劳动很多：找论文，追数据来源，下载和解压，再逐份判断读法、整理样本信息。每个步骤单看都不难，换一批数据，原来的假设却经常不够用。

Agent 很适合介入这样的工作。我早期试过给它更大的自由，让它自己写、改 loader。后来又收紧权限，把流程拆成固定阶段。这篇沿着数据整理的问题展开：为什么改方案，怎样把文件结构交给模型，以及文件读出来以后，哪些事情还没做完。

## 先把这条路接起来

BioFlow 的起点是文献检索。先在 PubMed 找论文，再下载 PDF，从正文里提取数据编号，沿着编号获取数据，最后构建数据集、整理元数据。

![BioFlow 的五阶段与模型介入位置](/images/bioflow/data-journey-zh.svg "根据项目设计说明与现有源码重绘的流程示意；表示分工，不代表每批数据都能走完。")

我把每一步的产物留下来。论文列表、下载状态、编号表，以及后面的数据文件，各自有自己的位置。这让修改一段流程时不必从头来过：下载失败就处理下载，读不了矩阵就去检查文件和 loader。

数据编号也只是入口。一篇论文可能引用多个研究的数据，正文出现了编号，不一定意味着那份数据就是我要收集的对象。编号提取先用正则，有效结果找不到时再让 LLM 补找；后面仍然需要判断数据是否适合当前研究。

不过，比“找到入口”更费心的，是入口后面那堆文件。

## 一份数据，往往不止一个文件

以常见的 10X 矩阵为例，一组文件里，`matrix.mtx.gz` 保存数值，`features.tsv.gz` 对应矩阵的特征，`barcodes.tsv.gz` 对应 barcode。读取时要把这三者配在一起。[10x 的格式说明](https://www.10xgenomics.com/support/software/cell-ranger/latest/analysis/outputs/cr-outputs-mex-matrices)

下面是说明这个问题的简化目录，样本名是示例，不是某次运行的截图：

```text
downloaded_dataset/
├── sample_A/
│   ├── matrix.mtx.gz
│   ├── features.tsv.gz
│   └── barcodes.tsv.gz
├── sample_B/
│   ├── matrix.mtx.gz
│   ├── features.tsv.gz
│   └── barcodes.tsv.gz
└── sample_metadata.tsv
```

只看扩展名，能找到两个矩阵，却不能据此决定怎么合并它们。`sample_metadata.tsv` 也是表格，但它不是另一份表达矩阵。实际附件还可能把样本编号放在文件名前缀里，或套几层压缩包，或已经提供 h5ad。要判断读法，就需要看到文件之间的关系。

我采用的办法，是先用程序提取目录结构、候选文件和少量文本，再把这些线索交给 AI。矩阵里的大量数值不需要塞进提示词；模型在这个环节要回答的是：哪些文件是一组，应该用哪种 loader，具体路径是什么。

![从目录线索到数据读取和样本映射](/images/bioflow/file-to-sample-zh.svg "按项目 probe、planner、样本解析与编号映射代码重绘。sample_A/B 为教学示例；loader 选择与样本编号整理是两个环节。")

对于 MTX 文件，计划里的一个 item 要同时包含 matrix、features 和 barcodes。把它们写成三个独立任务，会丢掉原本需要一起读取的关系。这也是我在提示词里明确写下的一条规则。

目录在这里不只是文件的摆放方式。它是给模型看的上下文，也是之后检查模型判断的依据：如果选错了文件，我能回到同一份目录摘要，看看它漏了什么、把什么当成了矩阵。

## 让 Agent 自己改代码，还是让它选工具？

早期我想过，既然 Agent 能写代码，遇到新的数据格式就让它自己补一个 loader。这样不用预先把所有读法都实现好，听起来很灵活。

我做过这方面的尝试，但异构数据上的幻觉和不稳定修改，让这个方向没有继续承担全部处理工作。一个 loader 改完能运行，还得检查它读的是不是正确文件、矩阵方向是否对、样本有没有合错。自由度越大，出了问题要检查的范围也越大。

后来我选择更有约束的工作流，类似 LangChain 式的显式编排：步骤、输入输出和工具分工先明确。模型可以根据文件结构判断读法，选择已有 loader；真正读取、转换和写文件交给程序完成。如果模型规划这条路没得到预期产物，外层 builder 再尝试确定性的构建方法。

这仍然给模型留下了需要判断的工作。文件名称不规范、说明藏在附件里、格式线索分散，都是它可以帮忙的地方。我收紧的是执行的范围，让一次判断能落到一个具体工具上，也能回到这个工具检查。

这次取舍改变了我处理错误的方式。比起追着一段临时生成的代码查，我更容易区分：是模型选错了文件，还是已有 loader 没处理好这种输入。

## 矩阵读出来了，样本还要对得上

构建出 h5ad 之后，还要知道里面的细胞属于哪个样本。后续按组织、时间或处理条件比较，都依赖这一步。

设计说明书里保留了这张关系图。它把 Dataset、Sample、Cell 和 Donor 分开，也说明了我为什么不能只保留一个数据集编号。

![BioFlow 原设计说明书中的数据关系图](/images/bioflow/sample-relations-original.webp "从 BioFlow v0.2 设计说明书中提取的原图，压缩为 WebP；这是数据关系设计，不是样本识别准确率或数据库部署结果。")

文件结构可以提供样本线索，但线索还要和样本记录对应。BioFlow 会读取可用的 SDRF 或 GEO series matrix 映射，也会从来源文件和目录解析编号。另一个 LLM 环节接收已有 sample_id、细胞数、来源文件或目录，返回旧编号到新编号的映射。

这和前面的 loader 选择不同：前者决定读哪些文件，后者整理已经读入的数据怎样标识样本。把两件事分开，才知道出错时应该检查哪一段。

模型返回映射后，程序会检查格式和部分完整性；失败时回退到路径生成的标识。路径标识至少能留下数据来源，但它不一定是正确的生物样本身份。一个字符串长得像 GSM，也不能单凭格式就确认它对应哪个供体、哪个条件。

因此，样本映射不能只看“有没有生成编号”。实际使用时还需要回看原始样本表，检查是否把两个样本合成一个、是否把同一个样本拆开。这里比提示词写得漂亮更值得花时间。

## 样本有了名字，还缺它的来历

样本对应之后，问题会继续往下走：年龄、组织、疾病状态和测序方法在哪里？数据库里有一部分，论文、补充表和文件名里也可能有一部分。同一个概念还会有不同写法。

我让模型对照原始材料和字段字典做提取、匹配与标准化。程序先处理能用规则确定的字段，再让 LLM 补缺；当前写回逻辑保留非空字段，只填空值或 `Unclassified`。因此，已有但不规范的值也可能留下，仍需要检查。

这类任务很适合用 AI 读文本，但有个容易忽略的问题：一个合理的答案，未必有材料支持。缺失年龄会让人停下来找来源，填错的年龄却可能直接进入分组分析，后面的代码还会顺利画出图。

所以我会把字段补全和数据可用分开看。补上一个值只是开始；如果它影响分析，应该知道它来自哪里，并回到原始材料核对。

不同模态也有不同的完成位置。RNA、ATAC 和空间数据继续走矩阵路径；蛋白、代谢和影像的扩展先收集文件、清单与样本信息。后一类尚未完成各自的定量处理，我没有把它们都包装成同一种“可分析矩阵”。

## 能跑一次，和能长期运行之间

固定五阶段之后，我仍然希望 Agent 能承担更多调度和纠错。早期的文献、下载与提取环节成功率不理想，也是我后来考虑重构和 Skills 的原因。

把每一步写成 Skill，能告诉 Agent 怎么操作，却没有自动解决任务的生命周期。下载超时应该重试，找不到合适数据不应该无限重试；进程重启之后，也需要知道哪一步已经完成。

Nova 的设计沿着这个问题继续：保留已有执行工具，在上面增加任务队列、状态和恢复。一次完整运行、单个任务、一次尝试分别记录。后来的 Sentinel 原型实现了其中一部分，包括 SQLite 状态库、worker、重试分类和 heartbeat。

我原先想增加 Agent 自主性，后来收紧执行权限，再考虑让它负责规划和异常处理。这里没有一个适合所有环节的自由度。判断文件关系需要灵活性，写产物、保存状态和安排重试则需要清楚的规则。

长时运行仍未全部验证。Sentinel 的历史小样只完成第一步，第二步失败后，后续阶段被阻塞。它说明状态和阻塞已经进入了流程，也说明这还不是一套可以放心无人值守的完整系统。

下一轮我会先用一小组固定数据，把文件、样本和元数据的对应关系逐项检查。比如合并两个矩阵之前，先确认它们来自哪些样本；补全一个年龄之前，先找到支持它的材料。继续增加数据量之前，我想先把这些对应关系做扎实。

早期脚本在 [Bio_dataflow](https://github.com/laowangbushilaowang/Bio_dataflow)；后续多组学扩展和 Sentinel 原型不全在这个公开仓库中。
