论文找到了，数据也下载了，接下来还要做多久？做 BioFlow 之前，这两件事离“数据能用”还隔着不少工作：解压附件、判断矩阵怎么读、找样本编号，再去网页和补充表里确认组织、年龄、处理条件。

我在广州实验室接到的任务，是在三个月内做一个 Agent，目标是替代人工收集和整理公开数据，为虚拟细胞模型准备语料。这是当时的任务目标。实际做下来，最难的部分一直是异构数据处理和元信息获取。

前面的[样本时间与拟时序研究](/zh/blog/niche-time-pseudotime/)已经让我碰过这种麻烦：想比较不同阶段的细胞，先得知道每个细胞来自哪个样本、样本是什么条件。数据整理出错，后面的模型也可以训练得很顺利，只是回答了另一个问题。

BioFlow 最后形成了五阶段流程：找论文、下载全文、提取数据编号、构建数据、整理元数据。我主要花时间做的是后两步，以及决定 Agent 在哪里可以自己判断。

![BioFlow五阶段流程](/images/bioflow/workflow-original.webp)

*五阶段的分工。各阶段保存中间产物，后一步接着前一步的结果处理。*

## 从自由 Agent 转向固定流程

我最初考虑过 LangChain 和更自主的 Agent 路线，也部署过本地模型，尝试让它遇到新格式时自己编写、修改 loader——也就是读取数据的程序。

这条路很诱人。公开附件没有统一包装：同样一个 CSV，可能是表达矩阵，也可能是样本说明；同样一套 MTX 文件，样本可以分目录存，也可以全部挤在一个目录里。如果每种情况都写规则，维护起来很累。

但让 Agent 现场改程序，又增加了一层问题。它可能选错文件，也可能把读取方式改错。最后生成了 h5ad，还得检查矩阵方向、基因名、样本是否合对。排错时，数据和临时生成的代码一起变，越来越难定位。

后来我采用固定工作流，把模型留在几个明确的判断点里。这里说的“LangChain 式”是显式编排的思路：步骤、输入输出和工具固定，并不表示所有阶段都依赖某个 LangChain 版本。

| 模型负责判断 | 提供给它的材料 | 程序负责执行 |
| --- | --- | --- |
| 数据入口在哪里 | 论文正文、数据可用性段落 | 提取、记录 accession；明显编号先用正则处理 |
| 用什么方式读文件 | 文件树、候选矩阵与少量文本线索 | 调用已注册 loader、转换矩阵、写文件 |
| 元数据怎样归一化 | 当前样本的原始信息、规范词表 | 补充缺失字段、保存结果与状态 |

这样，一个新格式不再意味着让模型重写整个读取过程。模型给出计划，已有工具按计划处理；模型路径失败时，外层 builder 还可以尝试确定性回退。

我并没有因此放弃 Agent。只是把“能自己想办法”拆开：哪些判断值得交给模型，哪些动作已经有稳定工具，不必每次重新发明。

## 文件结构，比把矩阵塞进上下文更有用

第四步收到的不是一张干净表格，而是一个目录。有时里面套着压缩包，有时同时放着原始矩阵、作者处理后的矩阵和 metadata。首先要弄清楚它们的关系。

例如，项目早期实际下载目录中有这样一组文件。这里只列其中几个，省略其他样本：

```text
GSE119562_RAW/
├── GSM3377673_sample1h.csv.gz
├── GSM3377674_sample2h.csv.gz
├── GSM3377675_sample3h.csv.gz
├── ...
├── GSM3377679_sample1m.csv.gz
└── GSM3377680_sample2m.csv.gz
```

这些名字已经提供了样本线索，但文件名后缀里的字母、数字是什么意思，不能凭外观补成研究条件。读取之前还需要看表头、矩阵方向和样本说明。

对于 MTX，关系又不一样。矩阵、features、barcodes 必须配成一组；如果把三个文件分别当成三个输入，程序就理解错了数据单位。同一目录下有多组带前缀的文件时，还要按前缀正确配对。

我做了一个探测层，提取相对路径、后缀、大小、候选文件和部分文本头。模型看到这些线索，输出一个简短 JSON 计划：选哪个 loader，每个样本要读哪些文件。它不需要看到整份表达矩阵。

从读取到合并，我把它分成三个环节：

1. **读取文件。** 比如用 MTX loader 读取一组 matrix、features、barcodes，得到细胞与特征的矩阵。
2. **确定样本身份。** 优先使用 SDRF 或 GEO series matrix 中的映射，也保留来源文件、来源目录等线索；需要时再让 LLM 辅助整理编号映射。
3. **合并后保留关系。** 细胞的样本编号要一起保存，才能继续关联年龄、组织或处理条件。

路径兜底至少能让来源不丢，但它不能证明样本身份已经核实。同样，编号映射格式正确，也不代表没有把两个样本误合成一个。需要回到原始样本表检查的，就是这些关系。

这部分开发里，我陆续加过多列 features、同目录多套 10X 文件、多样本合并、损坏 MTX 跳过、下载完整性检查等处理。它们共同解决的是：同一种数据被不同作者包装以后，仍然能按正确单位读进来。

## 元数据难在层级，也难在给模型看什么

读出矩阵后，还要回答：这些细胞来自什么组织？样本是对照还是处理组？年龄、疾病状态、测序技术分别是什么？

一篇文章可以包含多个供体，一个供体可以有多个样本，一个样本又对应许多细胞。把文章的一句话直接填给所有细胞，往往就出错了。

![Dataset、Sample、Cell与Donor的数据关系设计](/images/bioflow/sample-relations-original.webp)

*项目设计说明中的关系图。它的用处是分清信息属于哪一层：论文或数据集的描述，不能直接代替每个样本的条件。*

我把规则能确定的字段先整理出来，再让 LLM 结合原始材料补缺。信息来自 GEO SOFT、series matrix、ArrayExpress SDRF/IDF、样本网页，以及可用的补充表。

![元数据提取与填写流程](/images/bioflow/metadata-flow-original.webp)

*元数据处理流程：先区分数据集与样本信息，再按 sample_id 对齐，经过规则处理后交给 LLM 补充。原图裁自项目汇报。*

### ATAC 判错之后，我收紧了输入范围

后来同事在使用时反馈，ATAC 的组学类型和参考基因组会判错。这两个字段都很重要：选错组学，可能走错 loader；选错 genome，fragment 的坐标解释也会受影响。

排查时，我怀疑模型被混在一起的描述带偏了。GSE 是研究集合层面的说明，GSM 更接近具体样本的实验信息。我把这一步的判断上下文改为 GSM 信息摘要，要求忽略数据集层面的描述；拿不到 GSM 摘要时，就跳过 LLM 判断。

| 改动 | 解决的问题 |
| --- | --- |
| 从 series matrix 或 GSE 页面找 GSM 列表，再读取样本信息 | 把判断落到具体样本，减少研究概述混入 |
| 摘要含 Genome_build / Assembly 时优先采用明确版本 | 避免只凭物种猜测参考版本；这是提示要求，不是已验证的正确率保证 |
| 限制抓取 GSM 的数量，复用缓存 | 控制大量样本页面带来的下载开销 |
| 缺少 GSM 摘要时跳过 LLM | 信息不足时留下待处理状态 |

这个改动收紧了模型用于判断的信息范围；能提高多少准确率，仍需要用同一批数据对照。

第五步填写其他 metadata 时也有类似取舍：当前样本的那一行、与它匹配的补充表，应该优先于整篇研究的宽泛描述。我按信息块安排优先级和长度预算，避免一段很长的背景把真正有用的样本字段挤出去。

我后来与收数据的同事一起用、一起改。对方把实际遇到的问题反馈回来，我再尽量补成一类情况的处理方式。比起把一个失败文件单独修好，更有价值的是同样包装的数据下次也能处理。

## 怎样判断整理得对不对

最初，看到 `raw.h5ad` 或 `meta.h5ad` 生成，很容易觉得流程已经完成。检查人工整理的数据后，我才发现，“能读出来”和“整理一致”还差着好几层。

我写过一个对照 notebook：先取自动流程与人工整理库中共有的 GSE，再比较各字段出现过的取值集合。例如，一个字段在两边是否都出现 `Healthy`、`Tumor`，而不是只看列名存在。

| 那次对照 | 保存的结果 |
| --- | --- |
| 有比较结果的数据集 | 15 个；另有 1 个缺失结果 |
| 字段取值集合完全一致率，按参考字段数量汇总 | 39.31% |
| 各数据集一致率的平均 | 40.75% |

这两个比例**不是逐细胞准确率，也不是端到端成功率**。当一个 GSE 对应多个参考文件时，脚本还选择了集合一致率最高的一份，属于探索性比较。

双方同为空集合也会计为一致。取值集合相同，还可能把标签分配给了错误的细胞；集合不同，又可能是编号后缀、词表或整理范围不同。在一个实际对照中，两边都有 34,966 个细胞编号，但编号取值集合不一致；`sample_ID` 的集合相同，也不足以证明每个细胞的样本归属都正确。

因此这份比较更适合定位差异：是来源少了、命名没对齐，还是对应关系错了？下一步要逐项检查，而不是把它包装成一个总准确率。它也提醒我，字段填得越满，并不意味着数据越好。

早期 accession 提取另有一份运行结果：实际处理 43 条，31 条找到编号，12 条没找到，运行错误为 0。它只描述编号提取这一步，和上面的 metadata 对照不是同一批实验。

## 扩展组学，再考虑任务怎样恢复

RNA 路径逐渐成形后，我把 ATAC、空间数据等接入同一套流程。统一的是任务入口、来源和状态管理，数据本身仍要按组学处理。

| 数据 | 需要保留的区别 |
| --- | --- |
| RNA | 细胞与基因的对应，原始计数与处理后表达的区别 |
| ATAC | peak／fragment、参考基因组与条形码；不能照搬 RNA 清洗 |
| 空间转录组 | 表达与 spot 坐标的对应；缺坐标时明确记录 |
| 蛋白、代谢、影像 | 先收文件集合、样本信息和资产清单，定量分析仍需专门工具 |

后面几类走的是 collection-first：先把文件和来源整理好，输出清单，而不是统一改成 h5ad 就宣布标准化完成。

长期执行的问题则放到了后来的 Nova / Sentinel：通过 Skills 说明各阶段的输入输出，保存任务状态，区分临时下载失败和不适用数据，避免一个阶段失败后从头重跑。Nova 是设计，Sentinel 实现了部分队列、worker、重试与心跳；历史小样在第二阶段失败后阻塞了后续步骤，完整无人值守仍未验证。

BioFlow 后来用于团队的数据收集任务，也形成了软件著作权成果。回头看，最费心的工作是把人的判断拆细：哪份附件是矩阵，哪些文件是一组，这行 metadata 属于哪个样本，什么时候信息还不够。把这些关系讲清楚，模型和程序才各自有能做好的事。

早期代码见 [Bio_dataflow](https://github.com/laowangbushilaowang/Bio_dataflow)。后续多组学与 Sentinel 原型不全在这个公开仓库里。
