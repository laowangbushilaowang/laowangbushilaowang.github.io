把一个表达矩阵读进 Python，离“这份数据可以用了”还有一段距离。矩阵的行是细胞还是基因？条形码对应哪个样本？组织、时间点和处理条件写在文件名里，还是藏在论文的补充材料中？只要其中一个对应关系错了，程序可能照常运行，分析的对象却已经换了。

BioFlow 是我在广州国家实验室做的多组学数据采集与标准化项目，起点是为虚拟细胞模型准备数据语料。它把文献检索、论文下载、数据编号提取、数据集构建和元数据整理接成五个阶段。这里最费心的部分，是怎样保留来源与对应关系，同时让格式判断和文本解释不必全靠人逐份处理。

LLM 参与这些模糊判断，Python 工具负责实际下载、读文件和写结果。这个分工是尝试过更自由的 Agent 后收缩出来的：早期我试过让 Agent 动态编写、修改 loader，幻觉和错误修改让结果很不稳定。后来固定步骤，让模型选择已有工具。下面讲这条流程怎样处理编号、文件格式和元数据，再讲任务恢复。

早期脚本已放在 [Bio_dataflow](https://github.com/laowangbushilaowang/Bio_dataflow)。本文也涉及后来的多组学扩展和 Sentinel 原型，公开仓库不包含这里讨论的全部实现。

## 五个阶段，留下可以重读的中间结果

论文和数据并不是一对一的关系。一篇论文可以引用多份公共数据，一个研究系列又可以包含多个样本。GEO 的 `GSE` 是研究系列编号，`GSM` 是样本编号，二者对应不同层级。[GEO 检索说明](https://www.ncbi.nlm.nih.gov/geo/info/qqtutorial.html)

BioFlow 先从 PubMed 得到论文列表，记录标题、DOI 等信息；下载阶段给每篇论文留下状态。提取器读取已有 PDF，找出数据 accession，构建器再据此下载附件、判断格式，最后整理样本与数据集元数据。每个阶段都有自己的输入和产物，后一个阶段消费前一个阶段的结果。

![BioFlow 原项目汇报中的五阶段表](/images/bioflow/workflow-original.webp "原项目工作汇报第 2 页的五阶段表，导出后裁切并压缩。表中列的是流程、类名与产物，不是本次运行结果；点击可放大。")

这些中间文件让排障有了落点。提取不到编号，可以先看 PDF 是否存在、有没有可抽取的正文；矩阵没有建成，则去看下载目录和构建记录，不必重新检索整批论文。修了第四步的 loader，也能沿用前面已经完成的材料。

中间结果还有另一种用途：把“没做”和“做了但没找到”分开。缺 PDF、正文为空、正文里没有编号，会把任务送向不同的处理方式。只保存一个最终文件，下一次很难知道该从哪里接着做。

## 提取到编号，还没找到合适的数据

GEO、ArrayExpress 的编号有相对固定的形式，正则适合做第一遍扫描。当前提取器先匹配编号，再检查它是否出现在抽取的原文里、是否符合已知模式，并排除一部分明显的占位编号。有通过检查的结果，就直接返回；没有才调用 LLM。

这节省了模型调用，也带来一个取舍：正则找到一组编号后，模型不会再补找另一组。它没有同时做两路提取后求并集。

正文核对能拦下一部分模型凭空写出的编号，但“原文里有”只能建立很弱的关系。论文可能提到用于比较的外部数据，也可能在相关工作中引用另一个研究；编号真实存在，还要判断它和本文任务、目标组学有什么关系。当前校验没有完成这层判断，也没有给出经过人工标注的精确率或召回率。

2025-11-25 的一份实际 Step 3 报告记录了 200 行输入，其中 43 行进入处理，31 行提取到编号，12 行没找到，157 行跳过，运行错误计数为 0。报告把 `31/43` 写成了 72.1% 的成功率。这里的“成功”是有编号输出，范围只到提取步骤。

对照同批 CSV，更能看出这个数字的含义：31 条有编号的记录全部标为 `regex`；9 条走了 `llm`，没有提取到编号；另有 3 条标为 `failed`，也没有编号。仅凭这份报告，不能说 LLM 改善了提取效果，更不能说整条五阶段流程有 72.1% 的成功率。

CSV 还留了一个小坑：没找到编号时，`accession_code` 里可能是字符串 `Not found`。如果用“这个单元格非空”来计数，没找到也会被算进去。统计结果时，需要把状态字段、返回值和指标定义对上；表格填满了，并不意味着找到了更多数据。

## 模型选 loader，程序负责执行

下载目录里的文件很杂。有的数据给出稀疏矩阵、特征表和条形码，有的给一个 HDF5 文件，有的把每个样本打成单独的压缩包。决定怎样读它们，常常需要结合文件名、目录关系和少量文本说明。

BioFlow 的 `probe` 先整理相对路径、候选文件和文本片段，再把这些摘要交给 planner。模型返回一个 JSON plan，说明选哪个已有 loader、使用哪些 `items`。runner 查注册表，调用对应实现。矩阵的读取和转换仍由已有 Python 代码完成，AnnData、Scanpy 等库承担各自的数据结构与分析功能。

目录摘要在这里很有用：同样一个 `matrix.mtx`，与它并排的文件、所处样本目录以及上层说明，决定了它该怎样解释。模型需要看这些关系，没必要把矩阵里的每个数字读进上下文。probe 的目录枚举有文件数和深度限制，会标记截断；遇到被截掉的关键附件，仍可能选错。

当前 planner 用 JSON 解析模型回复，runner 只执行注册表里认识的 loader。这给模型限定了可选工具，但还没有完整的 plan schema 校验，也不构成操作系统层面的沙箱。文件读取权限仍由执行这些 loader 的进程承担。

如果模型选的 loader 没有构建出预期文件，外层 builder 在允许回退时再尝试确定性构建。这里要留意调用层次：主路径默认关闭 runner 内的 fallback loader 链，实际回退发生在外层 builder。只看 plan 中写着 `fallback`，会误以为列出的工具都已经试过。

这种安排方便逐个修格式适配，也保留了模型选错时的处理路径。不过，`raw.h5ad` 存在，最多说明一个构建产物已经落盘。矩阵轴是否正确、特征是否重复、条形码能否对上样本，仍需要针对数据检查。

## 多组学不必共用一种输出

[AnnData](https://anndata.readthedocs.io/en/stable/generated/anndata.AnnData.html) 把观测 × 特征的矩阵与 `obs`、`var` 等注释放在一起，适合已有矩阵表示的数据。RNA 可以用基因作特征，ATAC 常用 peak，空间转录组还需要把观测与位置接起来。

蛋白、代谢和影像附件未必已经处于这个阶段。原始质谱文件或显微图像，需要各自的处理方法才能变成可比较的数值。给它们套一个 `.h5ad` 后缀，处理工作不会自动完成。

扩展这些组学时，我要求保留已有 RNA/ATAC 流程，新类型先按各自需要接入。因此代码用 `OmicsProfile` 选择输出根目录、build mode 和 metadata mode：RNA、ATAC、空间转录组走各自的矩阵构建；蛋白、代谢、影像先采用 `collection_only`，收集文件、生成 manifest，整理 dataset/sample metadata。目录也按组学隔开。

![BioFlow 原项目汇报中的两类输出](/images/bioflow/output-modes-original.webp "原项目工作汇报第 3 页的输出模式表，导出后裁切并压缩。H5AD 与 Collection 是不同处理范围；表格不代表所有格式均已构建或验收。")

这让新组学可以先留下可查找的资产，而不用为它们编一个尚未实现的定量转换。当前 collection 模式没有完成蛋白、代谢的定量标准化，也没有替影像做分割和特征分析。空间转录组的接入重点是基本矩阵与 spot 坐标，不能把它扩写成完整的空间图像处理系统。

## 元数据里，空值有时比答案好

文件读出来后，样本的组织、物种、时间点、测序方法仍可能散在不同字段中。同一个概念可以有好几种写法，这正是模型比较适合参与的文本工作。

流程先用规则和词表处理已有字段，再给 LLM 原始 metadata 与相关文本，补充缺失值。样本级写回函数保留非空字段，实际代码中有这段检查：

```python
for key in LLM_FIELDS:
    if key not in parsed:
        continue
    if row.get(key, "Unclassified") not in [None, "", "Unclassified"]:
        continue
    updated.at[sid, key] = _normalize_field(key, parsed[key])
```

这个选择减少了模型覆盖已有信息的机会，也意味着已有但不规范的非空值不一定会在这一轮改正。模型调用或解析失败时，代码留下错误记录，继续保留原来的缺失状态。

`Unclassified` 可以提醒下游还缺材料。一个听起来合理的组织名或时间点则容易被直接拿去分组，直到分析结果异常，才发现条件是猜出来的。模型回复能解析、词语能归一化，都没有证明字段是真的。若要把这些补充值用于严格的跨数据集分析，我会再补字段级来源和人工抽查，而不是只统计填充比例。

## 长任务恢复需要执行状态

单个阶段能重新运行之后，接着遇到的是更长的任务：哪份论文卡住了，哪些下载值得重试，谁正在处理一个 accession，中断后应接哪一次尝试。

Nova 的设计把这些问题分成 Run、Task、Attempt。后来的 Sentinel 原型已经有 SQLite 状态库、worker、重试分类和 heartbeat：Run 记录整次任务，Task 记录一个工作单元，Attempt 保留每次尝试。worker 在 `BEGIN IMMEDIATE` 事务中选取依赖已完成的任务、标为运行中，再调用执行器；失败重试有自己的记录，不覆盖成仿佛什么都没发生过。

我在这次演进里提出过用 Skills 拆分阶段，也想让 Agent 从头推进到尾。真正运行时，Skill 文件只描述输入、输出和处理要求；worker、Python 执行器、状态库和依赖环境仍要工作。把五个步骤写成五个 Skill，不会顺便解决下载超时、并发领取或中断恢复。

Sentinel 还没有做到设计里的所有事情。watchdog 根据过期 heartbeat 把任务重新排队，但 heartbeat 在独立线程里更新：它能说明这个线程还活着，不能证明子进程持续取得进展。重新排队后，旧 worker 也可能迟到写回；当前完成更新没有核对新的领取身份，后续需要用 attempt/lease 身份拒绝旧结果，并让产物写入能安全重试。

第四、五阶段目前适配旧 CLI，以子进程退出码判断这层执行是否成功，还没有逐 accession 的产物质量验收；reconciler 也只返回队列状态统计，没有完成数据库与文件的双向核对。所以 `succeeded` 的含义仍要看它是哪一层写出来的。

历史 `tiny_e2e` 小样记录更直观：第一阶段成功，第二阶段永久失败，第三至第五阶段被阻塞等待处理。它没有跑完整条真实数据链路。这次复查通过了现有 8 项单元测试，覆盖部分状态转换、错误分类、重试和熔断；测试的范围与真实数据小样不同，还没有完整的端到端成功记录。

我接下来会先拿一组固定的小数据，把矩阵轴、样本对应和 metadata 来源做成验收条件，再补执行超时与旧 worker 写回保护。这样一次任务停下来时，才能知道下一步该重试下载、修格式，还是回到材料里核对样本。全自动处理更多论文的吸引力很大，但我现在更想先让“成功构建一份数据”有一个足够具体的含义。
