在 Hermes 里把主会话切到 `qwen-deep` 后，日志中出现了一个不太划算的现象：生成标题、判断工具是否可以放行的辅助请求，也在用 Deep。

那次本地部署只有一个推理 slot。主任务和辅助请求共用它，短请求也可能等在长请求后面。标题最终只有几个字，并不说明生成它的计算过程也很短。界面上看到的“慢”，可能包含模型推理、请求排队和工具等待；只盯着生成速度，很难知道应该改哪里。

这是我把本地 Qwen 接入 Hermes 时遇到的一个具体问题。本文记录的是 2026 年 8 月至 9 月的部署与调整：四档路由怎样工作，哪些配置真正改了，哪些优化还缺一组对照。

## 四个模型名，一份权重

这套环境用 `llama-server` 加载 Qwen 的 GGUF 文件，自建路由层对外提供 `qwen-fast`、`qwen-standard`、`qwen-deep` 和 `qwen-auto`。Hermes 把模型回复组织成 Agent 的工具循环，终端、浏览器等工具在各自执行环境中工作。我通过 Codex 做配置、迁移和检查；Hermes 框架、Qwen 模型与 llama.cpp 都是第三方组件。

四个名字对应同一份模型权重的不同调用策略。Fast 关闭 thinking，Standard 使用 `medium`，Deep 使用 `xhigh`；Auto 按规则选择档位。它们不会因为名字不同，就各自多出一张 GPU 或一个独立的推理进程。

所以两处 `auto` 很容易混淆。路由层的 `qwen-auto` 会检查输入再选档位；Hermes 辅助任务里的 `provider: auto`，在当时的配置下会沿用主模型。后者没有替标题自动挑一个轻量模型。主会话切到 Deep，辅助请求便可能一起切过去。Hermes 的[模型配置文档](https://hermes-agent.nousresearch.com/docs/user-guide/configuring-models)也说明了辅助任务的继承与独立指定方式。

客户端协议还隔着一层。模型服务提供 OpenAI-compatible API，并不意味着所有客户端都能直接接入。Claude Code 那条路径经过兼容网关，最小请求曾返回预设的测试标记；Hermes 使用自己的 provider 配置。一个客户端通了，另一个仍要单独检查请求格式和工具回传。

## Auto 的规则也会偏向 Deep

早期路由器的 Auto 没有额外调用一个模型来分类。它检查请求中的模型名、文本、媒体和工具信息，再按分支选档位。

8 月 31 日的 `choose_mode` 源码里，有两段值得连着看。下面保留原有条件，省略与此处无关的分支：

```python
for message in messages:
    # ... extract role and text ...
    if role == "tool" or contains_tool_result(message.get("content")):
        tool_results += 1

# ... after scanning messages ...
if tool_results or ERROR_PATTERNS.search(latest):
    return "deep", "tool-result-or-error"
```

`messages` 是整段传入的历史。这个版本只要见过一次工具结果，后面的请求就能满足 `tool_results` 条件，进入 Deep；它没有区分“刚刚失败，需要重新分析”和“前几轮顺利读过一个文件”。Agent 又恰好会不断使用工具，于是一个偏保守的规则很容易变成长期偏向 Deep 的规则。

这能解释为什么规则路由需要看完整对话中的行为。单独给它一句短问题，可能会选 Fast；给同一句问题附上含有工具结果的历史，可能会选 Deep。路由规则读了什么信息，比它叫不叫 Auto 更有用。这是早期源码的行为，不是对今天服务的复测。

我仍会为复杂任务保留 Deep。排查根因和改一句文字需要的推理不同。Qwen 的[官方模型卡](https://huggingface.co/Qwen/Qwen3.8-27B-FP8)提醒过：降低单轮推理深度，可能增加失败和重试，使整个任务反而更慢。这里真正要衡量的是任务怎样完成，而不只是第一句话多久出现。

## 主任务与辅助请求分别配置

9 月 1 日的记录显示，标题和审批等辅助任务仍是 `auto`，日志里也出现了辅助请求沿用 `qwen-deep`。同时，服务使用 `--parallel 1`，服务器还有其他训练负载。这几件事都可能增加等待时间，但当时没有逐请求的延迟分解，不能算出各自贡献多少。

我后来选择保留本地 `qwen-standard` 做主任务，把审批交给独立的 Codex 模型。9 月 3 日的修改记录中，审批最后设为 `gpt-5.3-codex-spark`；标题、压缩等任务并没有全部按最初建议拆成 Fast 或 Standard。

这是一个混合部署。主任务由本地模型处理，审批请求走另一个 provider，因此涉及审批的命令信息会离开本地模型服务。把它介绍成“所有处理都在本地”，就漏掉了这条调用路径。

独立配置审批有两个用途：可以针对这类判断选择模型，也能把这部分推理从本地单 slot 上移走。但审批仍然要花时间；我没有完成整套配置的 A/B 测试，也没有得到“总耗时降低多少”的结果。它更不等于操作系统沙箱。模型判断是否放行，与进程真正拥有怎样的文件和网络权限，是两回事。

标题等辅助任务固定走轻量档，仍是值得测试的方案。它解决的是短任务误用高推理档的问题；如果请求仍落到同一个本地进程上，排队并不会因此消失。要同时看路由选择和服务容量。[llama.cpp 的 server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)把 `--parallel` 定义为服务 slot 数；这个部署当时只有一个。

## `tool_calls` 只过了第一道检查

本地模型能聊天以后，还要检查 Agent 能不能真的使用工具。这里至少有几个不同动作：模型返回结构化调用，框架找到工具并执行，把结果带回下一次模型请求，再继续完成任务。

9 月 1 日的小测给四个路由都传了 `add_numbers`，参数是 19 和 23。实际输出摘要如下，去掉了耗时和推理长度：

```text
qwen-fast      finish=tool_calls tool=add_numbers args={"a":19,"b":23}
qwen-standard  finish=tool_calls tool=add_numbers args={"a":19,"b":23}
qwen-deep      finish=tool_calls tool=add_numbers args={"a":19,"b":23}
qwen-auto      finish=tool_calls tool=add_numbers args={"a":19,"b":23}
```

这说明四档都曾返回可识别的结构化工具请求，而不是只在正文里写“调用 add_numbers”。它还没有验证复杂工具参数、异常恢复或长任务完成率。模型给出请求后，真正执行加法的是工具；工具名称、参数和调用 ID 需要被框架正确接上，结果也要回到对应的调用中。

当时每档只测了一次，服务器负载也不一致。Deep 那次甚至比 Standard 更快，这不足以形成速度排名。若要比较推理档位，我会用固定任务集记录完成率、重复调用和总耗时，并把服务等待与模型生成分别计时。否则，刚好排到一个空闲 slot 的模型就容易获得一个漂亮但没用的名次。

还有版本区别：这次加载的是第三方修改、量化的 Qwen3.8-27B Aggressive GGUF，不能把官方原版模型的评估与行为直接搬过来。工具小测通过，也没有测出审批判断的可靠性。

## 上下文长度需要沿着链路对齐

这套服务的 context 参数为 262,144 tokens，最初 Hermes 只给 `qwen-auto` 登记了这个长度。切到其他别名时，客户端不能仅凭相似的名字知道它们共用同一个大窗口。

9 月 3 日，我批准补全四个别名的上下文登记，并开启工具循环硬停止。修改后的输出明确列出四个别名均为 262,144；本次查看静态配置，仍保留这些值。这里确认的是服务参数与客户端声明，没有做填满窗口的质量测试。

大窗口也需要资源预算。模型权重之外，还有保存上下文中间状态的缓存和运行时缓冲。把上下文调大、增加同时服务的请求，都会改变资源需求；slot 增加后，每个请求能用多少上下文，还要核对具体运行时版本。不能只把 `--parallel 1` 改成 2，然后默认两个会话都保留原来的容量与速度。

长任务还需要判断何时压缩，以及何时停下来。把压缩提前到约 160K、关闭自动后台 review 等，当时只是建议，没有全部实施。已经开启的硬停止则处理重复失败或无进展调用，不能替代产物检查：工具没有再报错，任务仍可能没有做对。

## 模型活着，客户端仍然超时

连接问题也得按链路查。一次检查中，服务器本机的模型健康与模型列表接口返回成功，外部网关仍然超时。模型进程在回答请求，客户端到它之间的路径却没有通。此时重新加载模型，未必碰得到故障位置。

更早的 Open WebUI 问题也有类似的错位：模型列表选不出来，直接访问本机模型接口却有结果。日志中，经代理访问这个接口返回 502；WebUI 进程继承了 `HTTP_PROXY`、`HTTPS_PROXY`。诊断后的修复方向是让本机地址绕过代理，但这份记录没有后续完整的界面验收，我不能把它写成已修复案例。

这两次检查留下的做法很具体：先在模型服务所在机器发最小请求，再从客户端所在机器测同一条链路，最后检查 Agent 的工具循环。每次尽量只跨过一个新增组件。否则，一个“连不上模型”可以同时指向代理、网关、服务排队和模型本身，反复重启很难增加信息。

这套环境已经留下了服务迁移、四档工具返回和部分配置调整的记录，还缺真实任务的路由对照。下一轮值得测的是：同一批任务，在主任务与辅助请求分开配置后，完成了多少、重试了多少、等待花在哪里。先知道时间被谁用了，再决定把哪一部分调快。
