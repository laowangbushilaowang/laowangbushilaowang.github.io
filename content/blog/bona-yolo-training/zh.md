这篇文章记录两项 YOLO 实践：在 Bona 实习时，我用公司数据改进家居目标检测；另一个是我自己采集游戏画面，尝试视觉辅助瞄准。两者使用不同数据、解决不同问题。公司部分讲模型改进与训练迁移，游戏部分讲怎样把数据、检测和动作串成一个可以反复改进的原型。

## 公司项目：扫地机器人的家居目标检测

我在 Bona 实习时，公司希望摄像头能认出地面上的物体：雷达和红外可以提供障碍信息，图像则有机会进一步分清前面是鞋、电线，还是家具。我拿公司已有的数据训练 YOLO。样本量有限，类别数量又不均衡，各类检测效果差得很明显；我因此从结构和 loss 两条线尝试改进，再通过消融比较改动有没有用。

这段工作发生在 2022—2023 年。按我对实验的回忆，单独更换 loss 后，`mAP@0.5` 相比原始 baseline 提升约 5 个百分点。Focal Loss 和 Varifocal Loss 我都考虑过，但已经记不清带来提升的具体是哪一种。

![原 PPT 保存的家居检测结果，画面中有鞋、家具腿和纸团的检测框](/images/bona/household-detection.webp "旧个人 PPT 保存的检测示例，展示家居目标的位置与类别；整体精度仍需看验证集。")

低机位的图像并不干净：鞋和电线贴着地面，家具遮住一部分视野，反光也会干扰外观。旧配置里能看到 `leg`、`wires`、`shoes`、`paperBall` 四类。我的工作是在公司数据上改模型、训练和评估，没有负责这批数据的采集标注，也没有把模型部署到机器人硬件。

### 先看数据：数量不均衡，数量多也未必学得好

我改 loss 的起点是训练数据。我记得有些类别表现不错，样本较少的类别却明显落后，当时也怀疑模型出现了过拟合。旧 PPT 还保存了一张分析文档的截图，里面有这份类别统计：

| 类别 | 训练集 | 验证集 | 测试集 |
| --- | ---: | ---: | ---: |
| 家具腿 `leg` | 3,488 | 885 | 446 |
| 电线 `wires` | 799 | 208 | 106 |
| 鞋 `shoes` | 1,836 | 465 | 259 |
| 纸团 `paperBall` | 1,831 | 542 | 224 |

这是旧记录中的类别标注数量，不是独立图片张数；一张图片可以包含多个目标。训练集的家具腿约是电线的 4.4 倍，鞋和纸团也各有电线的两倍多。模型从各类目标得到的训练机会并不相同。

但笔记里还有一个反直觉的观察：**数量最多的家具腿，检测表现反而较差。** 当时的分析怀疑这一类标注噪声较多，并把它与过拟合联系起来。这说明问题不能全归到“电线太少”：有多少标注、标得是否一致、是否覆盖不同外观，是不同的事。笔记还提出了扩充数据、检查标注和增加正则化几个方向。

这也解释了我为什么改 loss。对少数类加权，是调整不同类别对训练的贡献；Focal 则是减少容易样本对损失的支配。它们可以改变模型怎样利用现有数据，但错误标注也可能被当成难例，获得更大的权重。结构、loss 和数据质量得放在一起看。

过拟合还需要训练与验证的对照：训练表现继续变好，验证 loss 却上升，或验证 AP 停滞、下降，才是更直接的线索。几个类别之间的分数差距本身不能证明过拟合，也可能来自数量、标注或目标难度。检测任务里这里更适合看每类 AP、召回和误检，而不是把它们统称为“准确率”。[YOLO 训练与诊断建议](https://docs.ultralytics.com/yolov5/tutorials/tips-for-best-training-results)

### 改模型：地上的电线，和网络里的特征

这批数据里的目标差别很大。鞋有比较完整的轮廓，电线却又细又长；家具腿会遮住一部分物体，地面反光又会带来额外的纹理。检测器需要在同一张图里处理这些情况。与此同时，模型也不能只往大了做：我只有一张 2080 Ti，训练一个版本就要花很长时间。

我的结构尝试分成两条线：一条换 Backbone、Bottleneck 等模块，包括把 YOLOv5 的模块接进 YOLOv7，以及尝试 MobileNet 类轻量模块；另一条换注意力，让已有特征得到不同的权重。我也试过激活函数和 loss，再通过消融比较改动。

```text
输入图像 → Backbone：提取特征
         → Neck：融合不同尺度
         → Head：输出类别、框和分数
```

这几个位置不能混为一谈。Bottleneck 是网络内部的组件，Neck 是多尺度特征融合部分；换前者是在改变特征怎样计算，改后者是在改变不同尺寸的信息怎样汇合。当时我对一些模块理解还不深，能把它接起来，却不一定能解释为什么适合放在那里。这也是这段经历里很实际的一部分。

#### 注意力：保留有用特征，也别把细线压掉

我记得比较过通道注意力、空间注意力和两者结合。放回家居检测这个任务，它们的区别就比较容易理解了：通道注意力调整哪一类特征响应更重要，空间注意力调整特征图中的哪些位置更重要。

**通道不是 RGB 的三种颜色，而是网络学出的不同特征。** 以 [SE](https://arxiv.org/abs/1709.01507) 为例，它先对每个通道做全局平均，再用一个小网络生成权重，乘回原特征。256 个通道、压缩比例 16，对应 256 → 16 → 256 的权重生成过程。它保留特征图的尺寸，改变不同通道的贡献。

**空间注意力则保留位置关系。** CBAM 的空间分支沿通道取平均和最大值，把两张图拼起来，经过 7×7 卷积生成位置权重。反光和背景纹理可以受到抑制，但电线本身也很弱，不能把“压低响应”直接等同于“去掉干扰”。[作者实现](https://github.com/Jongchan/attention-module/blob/master/MODELS/cbam.py)

[CBAM](https://arxiv.org/abs/1807.06521) 把通道与空间加权串起来，先调整通道，再调整位置。它的通道分支同时使用全局平均和最大池化，与 SE 也不完全一样。

```text
原特征 → 通道加权 → 空间加权 → 后续检测
            保留哪些响应   关注哪些位置
```

这些原理解释了注意力为什么值得尝试，也解释了为什么不能只看平均分。鞋更容易被认出来，不代表电线也更容易被认出来；抑制背景的同时，也可能损失细小目标的信息。各类 AP、召回和误检，比一个总 mAP 更能说明改动是不是合适。原来的 loss 单项约提升 5 个百分点，不能算成注意力模块的收益。

#### 接 YOLOv5、MobileNet 类模块：接口要先对齐

我做过把 YOLOv5 的模块接进 YOLOv7 的尝试。这里接的是网络组件，和后来比赛里直接用 YOLOv5 模板训练是两回事。两套代码都叫 `Bottleneck` 或 `Conv`，也不代表参数和连接方式可以直接互换。

以 YOLOv5 的 C3 为例，它把输入分成两条路径：一条经过 Bottleneck，另一条保留较短路径，然后拼接，再用卷积融合。这可以帮助理解换模块时需要对齐什么，并不意味着换一个类名就完成了接入。[YOLOv5 模块实现](https://github.com/ultralytics/yolov5/blob/v6.2/models/common.py)

| 接口 | 要对齐什么 | 对不齐会发生什么 |
| --- | --- | --- |
| 输入 / 输出通道 | 模块接收的 `c1` 和输出的 `c2` | 下一层卷积无法接收输入 |
| 下采样倍数 | stride 与特征图高宽 | 多尺度分支拼接时尺寸不一致 |
| 残差连接 | 相加两端的形状 | 通道数或高宽不同，不能直接相加 |
| YAML 与模型解析器 | 模块名称、参数顺序、重复次数、层索引 | 模块建错，或取到了错误的特征 |

比如原模块的接口是 `[B, 128, 40, 40] → [B, 256, 20, 20]`，替换模块就得在这个位置完成对应的通道转换和下采样。这个形状例子说明的是接口约束，实际通道数随模型配置变化。若只换块、保持输出接口一致，后续 Neck 的改动较小；若换整段 Backbone，就要重新找到送进 Neck 的各尺度输出。标准 YOLOv7 的三个检测步长是 8、16、32，640×640 输入对应 80×80、40×40、20×20 特征图。[原始配置](https://github.com/WongKinYiu/yolov7/blob/main/cfg/training/yolov7.yaml)

我尝试 MobileNet 类模块，是另一条轻量化路线。以 MobileNetV2 为例，先用 1×1 卷积扩展通道，再逐通道做空间卷积，最后投影回输出通道；残差连接有形状条件。它减少一部分计算，但中间扩展出的特征也要占内存，训练显存和推理速度都不能只靠参数量判断。[MobileNetV2](https://arxiv.org/abs/1801.04381)

Ghost 模块走的是另一种思路：先用普通卷积生成少量特征，再用便宜的变换生成更多特征。YOLOv5、YOLOv7 都能找到 Ghost 类组件；使用一块 GhostBottleneck，也不等于把整个 Backbone 换成 GhostNet。[GhostNet](https://arxiv.org/abs/1911.11907)、[YOLOv7 模块实现](https://github.com/WongKinYiu/yolov7/blob/main/models/common.py)

这段工作让我分清了两件事：模块能接上，是结构和接口问题；检测有没有改善，是数据和实验问题。前向传播成功只解决了第一步，还要检查训练、梯度，以及导出后的输出是否一致。轻量化也有代价，尤其是电线这样的细小目标：计算省下来了，特征表达是否还够用，得放回同一验证集比较。模块名称听起来先进，不能替代这个判断。

### Focal 与 Varifocal：难样本和框的质量

面对前面的不均衡和类别差异，我考虑了 Focal 与 Varifocal，也对少数类增加过权重。类别权重回答“这一类占多少训练份额”；普通 Focal Loss 回答“这个预测已经容易到什么程度”。普通 Focal Loss 的直觉是：检测里容易的背景太多，让这些样本少占一些训练的注意力，留下更多空间给难例。它与“给少数类别加权”也有区别，前者按预测的难易程度调整，后者按类别调整。

先看普通 Focal Loss。假设背景的位置已经有九成把握被判对，另一个目标却只有一成把握被判对。我们希望模型少花点力气重复学习前者，把更多训练权重留给后者。

令 $p_t$ 表示模型给正确标签的概率，普通交叉熵是 $-\log p_t$。Focal Loss 增加一个随难易程度变化的因子：

$$
\mathrm{FL}(p_t)=-\alpha_t(1-p_t)^\gamma\log p_t.
$$

取 $\gamma=2$，预测正确标签的概率为 0.9 时，调制因子是 0.01；概率为 0.1 时，因子是 0.81。容易样本被大幅降权，难样本保留更多影响。$\alpha_t$ 是静态权重，$\gamma$ 决定降权的力度；这些数字是公式例子，不是我的实验成绩。[Focal Loss 原论文](https://arxiv.org/abs/1708.02002)

这也解释了为什么它适合拿来考虑检测里的前景/背景不均衡：容易背景的位置实在太多，即使每项损失很小，加起来也会抢走训练的注意力。不过难例中也可能有错标，不能只把 $\gamma$ 往上调，就期待效果一直变好。

Varifocal Loss 进一步关心**检测分数能否反映框的质量**。一个框很确信自己认出了鞋，却只框住半只鞋；另一个框更贴合物体，分数反而稍低。如果排序只看分类信心，前一个可能排在前面。VarifocalNet 用包含定位质量的目标分数来训练，尝试改善这种排序。[原论文](https://arxiv.org/abs/2008.13367)

![原 PPT 中保存的 Varifocal Loss 分段公式](/images/bona/varifocal-ppt.webp "旧 PPT 中的 Varifocal Loss 公式：正样本以定位质量 q 加权，负样本按预测分数降权。")

图里的 $p$ 是预测分数，$q$ 是训练目标：正样本通常取匹配框的 IoU，负样本取 0。IoU 是两个框交集面积除以并集面积。正样本用 $q$ 作为软标签，并以 $q$ 加权；负样本用 $\alpha p^\gamma$ 加权，让分数低的容易背景影响更小。这里的 $\alpha$ 用法也与普通 Focal Loss 不同。[作者实现](https://github.com/hyz-xmaster/VarifocalNet/blob/master/mmdet/models/losses/varifocal_loss.py)

下面只展示这个权重怎样乘到损失上。`logits` 是 sigmoid 之前的输出，`quality` 与它同形状，由正样本匹配结果和 IoU 构造；这是解释用代码，不是找回的历史训练实现。

```python
import torch
import torch.nn.functional as F

def varifocal_example(logits, quality, alpha=0.75, gamma=2.0):
    p = logits.sigmoid()
    weight = torch.where(quality > 0, quality, alpha * p.pow(gamma))
    bce = F.binary_cross_entropy_with_logits(
        logits, quality, reduction="none")
    return (weight * bce).mean()
```

真正接进 YOLO 时，还要确定哪个输出学习质量分数、怎样匹配正样本、怎样构造 $q$。把原来的 0/1 分类标签直接丢进这个函数，不等于完成了质量感知的训练。

比较时用到的 `mAP@0.5`，是按 IoU 达到 0.5 匹配检测框，再对各类别 AP 取平均。换了损失后，我关心的还是检测有没有改善，而不是新 loss 的数值是否更小。

### 一张 2080 Ti：训练预算也是实验设计的一部分

当时只有一张 2080 Ti。我会让一个方案训练一百多轮，直到 loss 几乎不再下降，一次完整试验可能要一天。想换的模块不少，这样做很快就把时间花完了。

现在回看，筛选阶段可以先给各方案相同的较短训练预算，在验证表现开始稳定时比较；留下有希望的，再充分训练。起步慢的方案要留复查机会。尤其不能跨损失函数直接比较 loss 的大小，它变小可能只是权重变了。

Batch 也不是越大越好。我遇到过显存不足，训练除了权重，还要存中间特征和梯度。今天会先用小 batch 跑完一步训练，测峰值显存，再逐步增加；梯度累积和混合精度可以作为新的尝试，不把它们写成当年已经做过的优化。

#### 少样本训练：改 loss 之外，还有哪些办法

这类问题有几种可以配合使用的方法。重点是先确定缺的是数量、多样性，还是标注质量，再选对应的训练方式。

| 方法 | 解决什么 | 需要注意什么 |
| --- | --- | --- |
| 预训练权重与微调 | 减少小数据从零学习特征的负担 | 可先冻结部分层再解冻；新加模块仍需训练，冻结过多也可能限制适应 |
| 清理标注、补采与增强 | 增加可信样本和外观变化 | 翻转、亮度、尺度变化须同步变换框；裁剪不能随意丢掉细线标签 |
| 少数类采样与类别加权 | 增加稀少目标参与训练的机会 | 检测按图片采样，一图可能多类；重复采同几张图也可能加重过拟合 |
| 正则化与早停 | 限制对训练数据的过度拟合 | 看验证指标选 checkpoint，不能因为训练 loss 还在下降就一直等 |

预训练与冻结部分层是小数据微调的一种路线，能节省计算，但冻结范围仍要通过验证比较。[迁移学习示例](https://docs.ultralytics.com/yolov5/tutorials/transfer-learning-with-frozen-layers)

**多折交叉验证解决的是评估是否稳定。** 以三折为例，轮流取一折验证、两折训练，独立训练三次，比较每类 AP 的平均值和波动。它不是把同一个模型连续训过三折；每折都要从同一预训练起点重新开始，最终测试集也不参与挑方案。它不会增加独立样本，也不会自动平衡训练数据。[交叉验证说明](https://scikit-learn.org/stable/modules/cross_validation.html)

如果数据里有同一采集片段或同一场景的相似画面，应整组分到同一折，避免近乎相同的图同时进入训练和验证。目标检测一图可能有多个类别，分折还得兼顾各类实例数和含类图片的分布，不能直接给整张图挑一个标签，就套普通分类的分层划分。

对于一张 2080 Ti，多折意味着多次训练。更实际的安排是先在固定验证集上筛选，把交叉验证留给少数候选。这里回答的是这类数据还可以怎样训练和验证；当时的类别记录与 loss 实验，是前面那段经历的依据。

### 昇腾比赛：先让训练跑起来，再谈改模型

公司这段工作之后，我参加华为比赛，尝试把训练放到昇腾 NPU 上。这次除了模型本身，还要先解决软件栈的兼容问题。

当时用的是面向 PyTorch 的适配环境。YOLO 与那套版本、算子支持之间出现了几处错误。我排查时怀疑某个矩阵计算相关函数有问题，但日志和最小复现没有留下来，现在不能把它说成已经定位的厂商 bug。后来我们改用 YOLOv5 模板，在昇腾服务器上训练。

我的体验是迁移麻烦，训练也慢。原本想把时间花在模型上，结果先花在了兼容性上。至少对当时那套环境，确实不太好用；慢在哪里、哪个算子出了问题，仍需要当年的版本和日志。

如果重做，我会先用平台已经适配的模型完成几步训练，核对输入、loss 和参数更新，再加回自己的改动。怀疑矩阵算子时，用一个独立小输入比较两端结果，比抱着整套 YOLO 一起调更容易定位。[昇腾 PyTorch 文档](https://www.hiascend.com/document/detail/zh/Pytorch/2600/index/index.html)


## 个人实践：游戏画面的视觉辅助瞄准

### 为什么开始做这个原型

想象这样一帧画面：准星停在屏幕中央，目标正在往旁边移动。模型框出它时，位置已经变了；程序再照着那个框调整，追的就是上一刻的位置。识别出了目标，动作仍可能跟不上。视觉辅助瞄准要解决的正是这段从“看见”到“动作”的时间差。

起点是《使命召唤》。我看到有人用 AI 识别游戏画面，再根据识别结果做辅助瞄准，也想自己试一下。当时我觉得，读取游戏内存的辅助方式已经过时了；从画面入手这条路线更值得尝试。这是我那时的想法，并不意味着视觉方案就没有自己的限制。

我做的原型需要从屏幕里找到目标，再把目标位置接到动作控制。这里的数据由我自己采集和标注，模型、截图和控制要配合起来。下面两张旧图来自我在 Apex 场景中做的原型。《使命召唤》的演示给了我起点，我随后自己准备数据，把这条思路做成程序。

![原 PPT 中游戏画面与检测预览并排显示](/images/bona/game-live-detection.webp "旧 PPT 中的原型：左侧是游戏画面，右侧是检测预览。这张图与下面的标注图均来自 Apex 场景。")

### 整个项目怎样循环起来

整个过程可以按四步来看，运行中的错误再回到数据端：

1. **采集和标注**：自己取游戏画面，标出目标，也加入容易混淆的队友。
2. **训练和导出**：训练轻量检测模型，导出 ONNX，再构建 TensorRT engine。
3. **实时运行**：截图、检测、选择目标，把位置偏差交给控制器。
4. **检查和补采**：看漏检、误识别与动作表现，补充对应场景，修正标签后再训练。

```text
① 采集与标注 → ② 训练与导出 → ③ 实时运行 → ④ 检查与补采
      ↑                                      │
      └──────── 新画面与修正后的标签 ────────────┘
```

四步不是一次性清单。第一次需要人工标注；有了模型后，可以先预标注再人工修正。下面按这个顺序讲我怎么做，以及每一步为什么需要它。

### 1. 数据：不仅要找敌人，也要区分队友

我的采集方式是鼠标点击触发，在短时间里每隔几毫秒取一帧，再拿去标注。具体间隔已经记不清，但这让我能很快补到当前场景的数据。

![旧游戏画面中对人物进行矩形标注](/images/bona/game-annotation.webp "旧 PPT 中的 labelImg 标注画面，已裁去本地文件路径。这是人物标注阶段的截图。")

只教模型找敌人，会遇到一个实际问题：队友也长得很像。我后来也标注相似的队友，让模型显式学习两者的区别。按我的经验，这比只标敌人更容易控制误识别，完整对照没有保存，所以没有具体的提升比例。

红框、蓝框或白框只是标注界面的显示方式，真正用于训练的是类别编号和框坐标。模型看到的仍应该是没有人工框的原始画面。

### 2. 模型：训练以后，还要导出加速

原生模型推理较慢，我采用轻量模型，走 PyTorch 权重 → ONNX → TensorRT engine 的路径。实时原型更关心一帧多久完成、显存能否承受，而不只是一个大 batch 每秒处理多少图。

ONNX 用来表示导出的计算图；TensorRT 再针对环境构建执行引擎。ONNX 本身不是自动加速按钮。旧归档中有 `.pt`、`.onnx`、`.trt`，`detect_trt.py` 也保留了加载 engine、准备 CUDA 张量与执行推理的代码。[TensorRT 部署说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/quick-start-guide.html)

截图提速和模型加速共同让实时链路更可用，但完整测速表没留下来，不能补报总延迟或加速倍数。显示出框之后，下一步仍是决定跟哪个目标、移动多少。

### 3. 运行：一帧图像怎样变成动作

这一段按运行顺序拆开，截图、模型和控制各自解决不同的问题：

```text
屏幕像素 → 预处理 → TensorRT 检测 → 选择目标 → 计算偏差 → PID → 动作
```

#### 截图与坐标：先把画面送进来

模型训好后，首先要把屏幕图像送进去。我比较过 PIL、其他 Python 截图库和 Windows 采集方式；印象里，后来截图压到了几毫秒，PIL 与 Windows 路径的差距也没有想象中那么大。这个时间只指截图，不是整个原型的响应延迟。

现存 `detect_trt.py` 里能核对 Windows 的采集路径：

| 步骤 | 代码里的做法 | 解决什么 |
| --- | --- | --- |
| 取屏幕区域 | 截取画面中心的 640×640 区域 | 限制每帧处理的数据量 |
| 复制像素 | Win32 `BitBlt`，再用 `GetBitmapBits` 读出 | 把屏幕区域变成像素数组 |
| 准备输入 | 缩放、填充、归一化和张量转换 | 满足模型的输入要求 |
| 还原位置 | 从输出框里扣除填充，再除以缩放比例 | 让框坐标对应回原始区域 |

代码还保留了注释掉的 `mss` 尝试。采集库只是这一段的一部分，颜色通道、复制次数、缩放都可能影响速度或正确性；这次回读旧代码，也发现颜色转换的返回值没有接回，值得重跑时检查。

今天再测速，我会固定区域和分辨率，分别测取像素、预处理、模型与控制，连续跑一段看中位数和较慢的一批，而不是只挑一次最快值。

#### 几毫秒到底花在哪一段

截图最终压到了几毫秒。接下来要看时间花在哪里：画面取得快，模型处理慢，目标的位置仍然会过时。

| 阶段 | 做法与经验 |
| --- | --- |
| 截取画面 | 比较 PIL、Python 截图库和 Windows 路径，把截图压到几毫秒 |
| 预处理与数据搬运 | 缩放、归一化、准备 GPU 输入；需要连同复制开销一起计时 |
| 模型推理 | 选择轻量模型，用 ONNX → TensorRT 加速，单独测单张图像的处理时间 |
| 检测结果与控制 | 整理框、选择目标、计算偏差，再由控制器给出调整量 |

先分段计时，才知道该继续优化截图，还是把时间花在模型和推理上。整段循环的耗时也要测，因为模型返回检测框之后，程序还得处理结果和执行动作。

旧代码的 `Done. (...)` 从截图之前开始计时，不是只测神经网络。不同版本还把绘图或控制放在不同位置，不能把这个数字直接抄成“YOLO 推理时间”。今天测 GPU 时，我会预热后再测，并用 CUDA event 或同步边界明确的计时；连续跑一段，报告中位数和较慢的 P95，而不只挑最快一帧。

#### 目标选择与控制：框出来以后怎样动

旧代码用离画面中心最近的候选作为目标，并设置距离限制和纵向偏移。这里的“最近”是选择规则，不是连续追踪；两个目标位置变化时，候选可能切换。今天升级，我会先处理连续帧的目标关联。

| 部分 | 输入与输出 | 它不负责什么 |
| --- | --- | --- |
| YOLO | 图像 → 类别、框、分数 | 不直接计算鼠标移动量 |
| 目标选择 | 多个框 → 本次关注的目标 | 不自动保证跨帧身份一致 |
| Kalman | 过去状态和新测量 → 估计位置 | 不识别敌人，也不代替动作控制 |
| PID | 目标位置偏差 → 调整量 | 不判断检测是否正确 |

Kalman 的思路是先根据过去的位置和运动预测这一帧，再用新检测修正。旧 PPT 记过这部分，但最终实现还没找到；目前能核对到的控制代码主要是 PID。

PID 在 `control.py` 中有实际实现。横向用了 P、I、D，纵向主要用 P，并不是两轴完全相同的控制器。

![旧 PPT 保存的 PID 函数代码](/images/bona/pid-original.webp "原 PPT 中的 PID 代码，与归档 control.py 对应：横向累积积分并计算微分，纵向采用比例项。")

P 根据当前偏差调整，I 累积历史偏差，D 看偏差的变化。检测框抖动、帧间隔不稳、动作过大，都可能让最终表现变差，所以要把位置测量和控制分开检查。漏掉一帧后继续预测、等待还是停止动作，也需要明确。

#### 几年后，在无人机论文里看到相近的思路

2022—2023 年做这个原型时，我已经在考虑把检测、连续的位置估计和控制接起来。原因很具体：YOLO 找到了目标，但框会抖，目标会移动，检测返回的位置也可能已经过时。只把一帧识别准确，还不够完成后面的动作。

几年后，我看到四川大学参与的 [Fast UAV Object-Searching in Large-Scale and Complex Environments](https://researchers.westernsydney.edu.au/en/publications/fast-uav-object-searching-in-large-scale-and-complex-environments/)，发表在 2025 年的 *IEEE Transactions on Cybernetics*。它把 YOLO 与 Kalman 结合，用于杂乱、容易遮挡环境中的目标位置估计，再服务于无人机搜索。让我有感触的是，我几年前做游戏原型时，就已经在想这条链路；后来看到相近的思路被放进无人机场景，做成了正式研究。

我的出发点是屏幕里的目标怎样接到控制，论文还展开了搜索策略、视点生成和路径规划。这也让我看到，从一个能用的原型到一项完整研究，还要把问题定义、方法和实验往前推进多少。当时的尝试规模不大，但那个“识别之后怎么办”的问题，确实值得继续做下去。

### 4. 看运行结果，再决定补什么

数据会随着使用继续补：采集、人工标注、训练，再看漏检和误识别，补采对应场景。有了初步模型，可以让它粗标，人工再修正类别和框，减少从零开始画的工作。不能省掉复核，否则原来的错标签会被喂回下一轮。

今天重建数据时，我还会按采集片段或场景划分训练和验证集。连续几毫秒的画面很相似，随机拆帧容易让验证成绩好看，却没真正检验新场景。

数据问题和运行问题要分别处理。相似队友被当成敌人，先回到样本和类别设计；检测位置已经过时，就分段测截图、推理和控制的耗时；框正确但动作抖动，则检查目标切换、位置估计和控制参数。不能遇到任何问题都再换一个检测器。

最终我搭起了采集、标注、训练到实时检测和相对控制的原型，旧 PPT 留下了展示画面，归档也保存了 `detect_trt.py` 与 `control.py`。截图压到几毫秒是我的回忆，完整全链路测速没有保留下来。原型基于已有 YOLO 方法，控制包在 README 中以团队编写描述。

这部分最有用的经验，是把模型放回实际使用过程里看：漏了什么，就补什么数据；慢在哪里，就测哪一段；检测对了却控制不好，就继续查控制。
