2022 年到 2023 年，我在 Bona 机器人公司实习。公司想给扫地机器人增加神经网络视觉识别：雷达、红外等传感器能提供距离和障碍信息，摄像头则有机会补充“前面是什么”。

我的工作是拿公司已有的数据训练和改进检测模型。数据采集、标注不是我的主责，也没有把模型部署到机器人硬件上。主要工作在训练这一侧：尝试网络模块、损失函数和训练策略，用消融实验比较改动，再在华为服务器上训练。用过 YOLOv7，后期也做了 YOLOv5 的训练。

这段实习里，值得回头讲的有三个问题：模型为什么学不好某些样本，怎样判断一次改动有没有用，以及怎样避免把一天的训练时间花在一个说不清理由的改动上。同期还做过一个实时视觉控制原型，那里遇到的是另一种问题：检测到目标以后，程序该怎么动。

## 摄像头看见的，是离地面很近的房间

![低机位室内照片中的拖鞋、电线和反光地面](/images/bona/household-input.webp "旧工程保存的输入样例：留意拖鞋、电线与地面反光。不是检测结果，未确认它属于最终训练集。")

这张照片比模型结构图更能交代任务。画面贴近地面，拖鞋、电线和家具挤在同一个视野里，还有瓷砖的反光。模型需要回答两个问题：东西是什么，在哪里。只给整张图一个“有鞋”的标签，机器人仍然不知道鞋占了哪块位置。

旧工程的一份家居配置列了四个类别：`leg`、`wires`、`shoes`、`paperBall`。它说明了当时工程里考虑过的检测对象；这里不把这份配置直接当成最终模型的类别表。

YOLO 输出的是框、类别和分数。网络前面的 backbone 提取图像特征，中间的特征融合部分让不同尺度的信息汇合，最后的检测头给出预测。在这样的模型上，我可以尝试替换提取特征的模块，也可以调整训练时什么样的错误更值得关注。

## 改网络之前，要知道想改善什么

当时我尝试过 MobileNet 等轻量模块，也试过注意力、激活函数，以及在 backbone、bottleneck 等位置做替换。公司数据中的类别不均衡和困难样本，是这些尝试要面对的问题。

现在回头看，我对部分结构的理解还不够深。知道一个模块有人用、可以放进去，与知道它为什么适合当前问题，之间还有一段距离。我做了消融，但也花了不少时间把候选完整训练到 loss 不再下降。

如果今天重做，我会先把错误分开看，再决定改哪一块：

| 看到的现象 | 更值得先查什么 |
| --- | --- |
| 小目标经常漏掉 | 输入分辨率、目标在图中的尺寸、多尺度特征 |
| 有框，但位置偏得多 | 标注、坐标变换、定位损失 |
| 两个类别分不清 | 每类样本、混淆情况、针对性增强 |
| 背景也被框成目标 | 误报样例、置信度阈值、负样本 |

这是今天的检查方法，不是说当年已经确认出现了表里的每一种错误。它的作用是把“再加一个模块”变成一个可以检验的假设：改完以后，哪一类错误应该减少？

## Focal Loss：让容易样本少占一点训练份额

损失函数是我改过的一部分。普通交叉熵会给预测错误的样本更大的损失，但检测任务里容易样本可能非常多。单个样本的损失小，不代表它们加起来的影响也小。

这里有两种不均衡需要分清：一张图中大部分候选位置都是背景；目标类别之间的样本数量也可能相差很大。Focal Loss 主要按当前样本的难易程度降权，类别权重则按类别加权。同一类别里也有容易和困难样本，不能把两种方法混为一谈。

用二分类的形式看最直观。令 $p_t$ 为模型给正确标签的概率，交叉熵是 $-\log p_t$；Focal Loss 在它前面增加一个因子：

$$
\mathrm{FL}(p_t)=-\alpha_t(1-p_t)^\gamma\log p_t.
$$

$\gamma$ 控制对容易样本降权的力度，$\alpha_t$ 是静态权重。假设 $\gamma=2$，只看调制因子：

| 对正确标签的概率 $p_t$ | $(1-p_t)^2$ | 对这项损失的影响 |
| --- | --- | --- |
| 0.9 | 0.01 | 已经预测得不错，权重降得很多 |
| 0.5 | 0.25 | 仍不确定，保留一部分 |
| 0.1 | 0.81 | 错得明显，降权较少 |

*这是按公式计算的教学例子，不是项目实验数据。因子乘在损失上；反向传播时它本身也参与求导，表中数字不是梯度倍率。*

下面用几行 PyTorch 展示同一个意思。`logits` 是 sigmoid 之前的输出，`targets` 为 0 或 1；这是解释用的独立实现，不是恢复出的历史训练代码。

```python
import torch.nn.functional as F

def focal_binary(logits, targets, alpha=0.25, gamma=2.0):
    ce = F.binary_cross_entropy_with_logits(
        logits, targets, reduction="none")
    p = logits.sigmoid()
    pt = p * targets + (1 - p) * (1 - targets)
    alpha_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (alpha_t * (1 - pt).pow(gamma) * ce).mean()
```

这里的 `alpha` 给正样本的静态权重是 0.25，负样本是 0.75；多类别问题需要另行设计权重；可对照 [Torchvision 的二分类实现说明](https://docs.pytorch.org/vision/main/generated/torchvision.ops.sigmoid_focal_loss.html)。参数不是越大越好，也不是复制论文默认值就能保证提升。具体原理见 [Focal Loss 原论文](https://arxiv.org/abs/1708.02002)。

YOLOv7 的[官方损失实现](https://github.com/WongKinYiu/yolov7/blob/main/utils/loss.py)本来就有 Focal Loss 的分支。我的工作是结合数据尝试和评估这种训练选择，Focal Loss 和 YOLO 本身都是已有方法。

按我后来对实验的回忆，加入 Focal Loss 后，`mAP@0.5` 相比原始 baseline 约提升了 5 个百分点。原始实验表没有找回，保存的几份超参还把 `fl_gamma` 设为 0，所以不能拿现存代码证明那次实验，也不能凭记忆拆出其他模块各贡献了多少。这是一项回忆中的结果，暂时无法补齐完整对照。

## 一个方案训练一天，试验很快就变贵了

我以前常把一个改动训练一百多轮，直到 loss 不再下降。一次完整试验可能要一天。结构、损失、权重都可以改，候选一多，时间就不够用了。

后来回顾这段工作，我想到可以先看前面一段训练的下降情况。这个想法还需要补一条：**不同损失函数的数值不能直接用来排模型名次。** Focal Loss 自己就会缩小容易样本的损失，把它和普通交叉熵的 loss 比较，低了未必是检测更好了。

今天我会把试验分两段。先给候选相同的短训练预算，检查训练是否正常，以及验证指标有没有值得继续的趋势；筛掉明显无效的候选后，再让少数方案完整训练。短预算也可能误杀起步慢的方案，因此边界候选要复查。最后仍靠同一验证口径决定保留，不把早期 loss 当成最终效果。

消融也需要把问题问窄。只换损失，就保持数据划分、输入尺寸、增强和训练预算一致；单项有价值，再试组合。否则一个分数上去了，很难知道到底是哪个改动起作用。

`mAP@0.5` 衡量各类别检测 AP 的平均值，匹配还要求框的 IoU 达到 0.5。它比整图分类的 accuracy 更贴近检测任务，但平均分也会藏住某些类别的退步。我会同时看每类 Precision、Recall、AP 和错误图片。这些是重做时会采用的评估安排，不是补写一份当年的实验记录。

## 检测以后还要行动：另一个实时控制原型

同期的游戏画面原型，把模型的输出接到了控制。它与扫地机器人检测属于不同任务，不能把这里的 TensorRT 或 PID 说成机器人上运行过的系统。

按旧代码整理，主要流程是：

```text
窗口或屏幕画面
  → 缩放与补边到 640×640
  → TensorRT 推理，得到框和分数
  → 恢复框坐标、筛选目标
  → 目标点相对画面中心的偏差
  → 控制计算、相对移动
  → 读取下一帧
```

这里有两个比“画出一个框”更具体的判断。首先，同一帧可能有多个框，程序要选一个；原型用离画面中心最近的目标，并加了距离限制和纵向偏移。其次，检测框会逐帧变化，直接把每次误差全部变成移动量，可能出现过冲或抖动。控制器需要根据误差安排移动。

旧控制模块里，横向用了 P、I、D，纵向主要用 P。P 看当前偏差，I 累积过去偏差，D 看偏差变化；它是带经验参数的原型，不是完整、对称的二维 PID。这条工程线以官方 YOLOv7 为基础，控制包在 README 中记为团队编写。

工程还保存了 `.pt`、`.onnx` 和 `.trt` 文件。README 特别提醒在运行机器上编译 TensorRT engine，并注明了一份 RTX 3070 / CUDA 11.7 的环境。模型权重与为具体环境构建的推理 engine 要分别管理；兼容范围还要看 [TensorRT 的版本和硬件约束](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)。旧材料没有完整时延对照，能核对的是推理与控制的实现链路。

这段经历里，我做的是公司数据上的模型迭代，也尝试过把检测接到实时控制。今天再开始一次这样的工作，我会先拿出误检和漏检的图片，写清楚这轮想减少什么错误，再打开模型配置。先把问题定清楚，才值得等下一天的训练结果。
