一个模型改动训练一天，再换一个模块，又是一天。这是我在 Bona 实习时做 YOLO 实验的节奏。手里是一张 2080 Ti，想试的东西却不少：网络结构、注意力、损失函数、类别权重。把这些都完整训练一遍，很快就会发现，限制试验数量的还有时间。

2022 年到 2023 年，公司想给扫地机器人增加神经网络视觉识别。雷达、红外等传感器可以提供障碍信息，摄像头有机会进一步回答“前面是什么”。我主要围绕公司已有数据做模型训练、修改和消融，没有负责这批数据的采集标注，也没有把模型部署到机器人硬件。

后来，我把检测与优化的经验迁移到游戏画面，自己采集、标注数据，把检测接到实时控制。再后来参加华为比赛，又要处理昇腾上的训练适配。三段工作给我的约束很不同：第一段要控制试验成本，第二段要让数据和速度一起跟上，第三段则先得让程序跑起来。

## 在 2080 Ti 上，怎样把训练时间花得更值

![室内低机位照片里的拖鞋、电线和地面反光](/images/bona/household-input.webp "旧工程保存的输入样例，未添加检测框，也未确认属于最终训练集。留意低视角下的拖鞋、电线和地面反光。")

扫地机器人的视角离地面很近。鞋、电线、家具和反光挤在画面里，模型既要认出物体，又要给出位置。旧工程的一份配置列了 `leg`、`wires`、`shoes`、`paperBall` 四类，能说明这类任务在关心什么；最终训练集和权重的完整对应关系没有留下来。

### 换模块，到底在换什么

我尝试过 backbone、bottleneck 的替换，包括 MobileNet 等轻量模块，以及注意力、激活函数。也做过消融：只改变一部分，看改动有没有用。当时对一些结构理解不深，知道它能接进去，还不一定能说清为什么该接在那里。

把网络拆开，会更容易讨论：

```text
图像 → Backbone：提取特征
     → Neck：融合不同尺度的特征
     → Head：输出位置、类别和分数
```

Bottleneck 是可能出现在网络内部的模块，不是 Neck 的另一个名字。要说明“换了模块”，至少得知道换的是特征提取、尺度融合，还是预测输出。

下面列的是**帮助理解结构的候选例子**，不是恢复出来的当年消融清单：

| 位置或模块 | 它改变什么 | 需要比较什么 |
| --- | --- | --- |
| 普通 Bottleneck / CSP Bottleneck | 卷积变换、残差与分支组织 | 精度、显存，以及增加分支是否真有收益 |
| MobileNet 风格的深度可分离卷积 / Ghost 类模块 | 减少部分计算开销 | 实际速度与丢失的检测能力 |
| Neck 的多尺度融合、SPP / SPPCSPC | 让不同尺度和范围的信息汇合 | 小目标是否改善，融合开销是否值得 |
| Detect / IDetect 等检测头 | 将特征变成框和类别预测 | 输出格式、训练匹配，以及导出兼容性 |

这些例子可以对照 YOLOv7 的[模块代码](https://github.com/WongKinYiu/yolov7/blob/main/models/common.py)与[检测头实现](https://github.com/WongKinYiu/yolov7/blob/main/models/yolo.py)。模块少、参数少，不保证在手里的设备上就快；最后还得实测。检测头也不是改个名字就能换，损失、标签匹配和导出路径都可能跟着变。

### 收敛得差不多，就可以先比较

我以前会让一个方案训练一百多轮，直到 loss 几乎不再下降，一次完整试验可能要一天。现在回头看，筛选阶段没必要每个方案都等这么久。

先保持数据划分、输入尺寸和训练预算一致，看验证集表现开始稳定时，哪些方案值得继续。明显无效的先停，留下少数候选做完整训练；起步慢的方案要留一次复查机会。最后的成绩仍需要充分训练，不能把一次短跑写成最终排名。

这里尤其要小心：**换了损失函数，loss 的数值不能直接横向比较。** 一个损失更小，可能只是它给样本乘了更小的权重。我会看同口径的验证指标，再看漏检、误检的图片，避免只盯着一条下降曲线。

`mAP@0.5` 是按 IoU 达到 0.5 来匹配预测框，再对各类别 AP 取平均；IoU 就是两个框的交集面积除以并集面积。平均分之外，也要看哪个类别变好了、哪个退步了。

### Batch 太大，先遇到的是显存

另一个坑是 batch size。一次送进去的图太多，训练会显存不足，通常表现为 `out of memory`；这和数值计算的“溢出”是两回事。训练还要保留中间特征、梯度等内容，显存占用不只取决于模型文件有多大。

我确实遇到过 batch 过大的问题。今天再处理，我会先用小 batch 跑通完整的一步训练，确认峰值显存，再逐步增加。梯度累积、混合精度也是可以考虑的办法，但不是说我当年已经用过：累积会改变更新节奏，混合精度也需要检查稳定性。输入分辨率、模型宽度和 batch 要一起算，不能只把 batch 调大就指望更快。

### Focal Loss 怎么改变训练的注意力

损失函数是我改过的一部分。普通交叉熵会给预测错误的样本更大的损失，但检测任务里容易样本可能非常多。单个样本的损失小，不代表它们加起来的影响也小。

这里有两种不均衡需要分清：一张图中大部分候选位置都是背景；目标类别之间的样本数量也可能相差很大。Focal Loss 主要按当前样本的难易程度降权，类别权重则按类别加权。同一类别里也有容易和困难样本，不能把两种方法混为一谈。

用二分类的形式看最直观。令 $p_t$ 为模型给正确标签的概率，交叉熵是 $-\log p_t$；Focal Loss 在它前面增加一个因子：

$$
\mathrm{FL}(p_t)=-\alpha_t(1-p_t)^\gamma\log p_t.
$$

$\gamma$ 控制对容易样本降权的力度，$\alpha_t$ 是静态权重。假设 $\gamma=2$，只看调制因子：

| 对正确标签的概率 $p_t$ | $(1-p_t)^2$ | 对这项损失的影响 |
| --- | --- | --- |
| 0.9 | 0.01 | 已经预测得不错，权重降得很多 |
| 0.5 | 0.25 | 仍不确定，保留一部分 |
| 0.1 | 0.81 | 错得明显，降权较少 |

*这是按公式计算的教学例子，不是项目实验数据。因子乘在损失上；反向传播时它本身也参与求导，表中数字不是梯度倍率。*

下面用几行 PyTorch 展示同一个意思。`logits` 是 sigmoid 之前的输出，`targets` 是与输出同形状的浮点张量，值为 0 或 1；这是解释用的独立实现，不是恢复出的历史训练代码。

```python
import torch.nn.functional as F

def focal_binary(logits, targets, alpha=0.25, gamma=2.0):
    ce = F.binary_cross_entropy_with_logits(
        logits, targets, reduction="none")
    p = logits.sigmoid()
    pt = p * targets + (1 - p) * (1 - targets)
    alpha_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (alpha_t * (1 - pt).pow(gamma) * ce).mean()
```

这里的 `alpha` 给正样本的静态权重是 0.25，负样本是 0.75；多类别问题需要另行设计权重；可对照 [Torchvision 的二分类实现说明](https://docs.pytorch.org/vision/main/generated/torchvision.ops.sigmoid_focal_loss.html)。参数不是越大越好，也不是复制论文默认值就能保证提升。具体原理见 [Focal Loss 原论文](https://arxiv.org/abs/1708.02002)。

YOLOv7 的[官方损失实现](https://github.com/WongKinYiu/yolov7/blob/main/utils/loss.py)本来就有 Focal Loss 的分支。我的工作是结合数据尝试和评估这种训练选择，Focal Loss 和 YOLO 本身都是已有方法。

按我后来对实验的回忆，加入 Focal Loss 后，`mAP@0.5` 相比原始 baseline 约提升了 5 个百分点。原始实验表没有找回，这个数字保留为我的回忆，不补画各模块的成绩。

## 游戏的数据自己采：不能只教模型认敌人

游戏这边的数据由我自己采集。鼠标点击触发采样，在短时间里隔几毫秒取一帧，再拿去标注。这样能迅速积累当前场景的画面，不过具体采样间隔已经记不清了。

我觉得有用的一点是：**只标注敌人，还不够。** 队友长得相近，也是模型容易弄错的对象。如果希望程序只对敌人作出反应，可以让模型同时学会“这个是队友”。只标敌人时，队友也能作为背景负例；单独设一个队友类别，则把这个区分显式地交给模型，收益仍要看数据和验证。

标注时，可以用红框表示敌人，蓝框或白框表示队友。但这些颜色只是标注界面的区分方式，真正训练的是类别编号和框坐标；人画上去的框不应该出现在训练输入里。模型要从原始画面的线索区分这两类。

按我的经验，把相似的队友也单独标出来，比只教“找敌人”更容易控制误识别。完整对照没有保存，所以这里讲的是数据设计经验，不给一个凭空的成功率。

数据也不是采一次就结束：

```text
采集画面 → 人工标注 → 训练模型 → 看漏检与误识别
    ↑                              ↓
    └──── 补采对应场景 ← 找出缺少的样本

已有模型 → 粗略预标注 → 人工修正类别与框 → 加入下一轮训练
```

模型先画一个大致的框，人工再微调，能减少从零开始标注的工作。但预标注必须复核，不然模型原来的错误又会被当成正确答案喂回去。

如果今天重建这个数据集，我还会把相邻视频帧留在同一划分里，尽量按采集片段或场景分训练、验证集。几毫秒间隔的画面很相似，随机拆帧容易让验证集看起来很好，换个场景却不行。这是现在补上的检查方法。

## 实时推理：先比较截图，再比较模型

训练时等一天很烦，推理时慢一点则直接影响动作。游戏的画面一直在变，模型看到的可能已经是刚才的目标位置。

我比较过 PIL、其他 Python 截图库和 Windows 的采集方式。印象里，后来截图能压到几毫秒，PIL 与 Windows 路径的差距也没有想象中那么大。原始测速表没有留下来，这个时间只指截图，不能当成整个检测控制系统的延迟。

旧代码能看到 Windows 的 `BitBlt`：从窗口或桌面的设备上下文复制位图，再读成数组；同时也保留了 `mss` 的尝试痕迹。这让“用 Windows 截图”有了具体含义。PIL 的 [`ImageGrab`](https://pillow.readthedocs.io/en/stable/reference/ImageGrab.html)则提供了更方便的截图接口。

如果今天重新比较，我会把测量范围写清楚：同一个区域、同样分辨率，是只计取像素，还是也包含转成模型输入？存 JPEG 的时间另记。单次最快值没什么用，连续运行时的中位数和较慢的一批也要看。

### 从 PyTorch 到 ONNX，再到 TensorRT

原生模型推理比较慢，我用轻量模型，再走 ONNX、TensorRT 的路径。这里对显存的考虑和训练不同：实时输入是一帧一帧来的，更关心每一帧多久完成，而不是一个大 batch 每秒吞多少图。

```text
训练得到 PyTorch 权重
    → 导出 ONNX：表示计算图
    → 构建 TensorRT engine：为目标环境优化
    → 加载 engine，执行实时推理
```

**ONNX 不是自动加速按钮。** 它让模型换一种可交给后续工具处理的表示；[TensorRT 的 ONNX 部署流程](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/quick-start-guide.html)说明了导出和构建的区别。具体加速发生在哪一步，要看后端、支持的算子和构建配置。旧工程确实保存了 `.pt`、`.onnx` 和 `.trt`，实时入口也有 TensorRT 推理代码。

我当时倾向最轻量的模型，因为推理速度和显存都有限。今天我会在候选中同时比较精度、单帧延迟和峰值显存，先找到能满足实际延迟要求的模型，再谈多一点精度。TensorRT engine 的[硬件和版本兼容范围](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)也要单独管，不能把某台机器生成的 engine 当成通用权重。

整个程序的等待还包括截图、缩放、数据传输、后处理和控制。GPU 操作有异步执行，直接用 Python 前后时间相减，可能只量到提交任务的耗时；测 GPU 段应按 [PyTorch 的计时说明](https://docs.pytorch.org/docs/main/notes/cuda.html#asynchronous-execution)使用同步或 CUDA events。只报“模型几毫秒”，解释不了实际动作为什么慢。

## 检测框怎样变成动作

检测输出一堆框，程序还得选择目标，再决定移动多少。旧代码中，目标选择用了离画面中心最近的候选，带距离限制和纵向偏移；控制器则横向用 P、I、D，纵向主要用 P。这条工程线基于 YOLOv7，控制包在 README 中记为团队编写。

P 根据现在的偏差算移动量，I 累积过去的偏差，D 关注偏差的变化。它们的用途是调节动作，不是判断框里是谁。位置测量抖动、推理延迟、动作过大，都会影响最终表现。

卡尔曼滤波解决的又是另一件事：用前面的状态预测这一帧的位置，再用新检测修正它。检测后的关联与估计也可以参考 [SORT](https://arxiv.org/abs/1602.00763) 的思路。各部分职责是：

```text
画面 → YOLO：目标在哪里、是什么
          ↓
      目标关联：跟上一帧的哪个目标对应
          ↓
      状态估计：例如 Kalman，平滑与预测位置
          ↓
      控制器：例如 PID，根据偏差安排动作
```

*这是解释职责的结构示意，不是宣称旧代码完整实现了上面每一层。现存代码能核对 PID；Kalman 在旧个人材料里有记录，对应的最终实现还没找回。*

我还记得一篇无人机相关论文也是 YOLO 后接位置估计，不过学校和题目记不清了。现在能找到的一个延伸阅读是 2025 年的 [Fast UAV Object-Searching in Large-Scale and Complex Environments](https://researchers.westernsydney.edu.au/en/publications/fast-uav-object-searching-in-large-scale-and-complex-environments/)，有四川大学参与，介绍了 Kalman 与 YOLO 结合的位置估计。它不一定是我记得的那篇，也不能由此推断论文用了 PID。

今天再升级这个原型，我会先处理连续帧的目标关联，避免每一帧都切到“当前最近”的另一个目标；再让位置估计用实际帧间隔和测量延迟，最后调整控制参数。没有新检测时，是短暂预测、等待还是停止动作，也需要明确。这些比单纯再换一个检测器更接近实时控制的问题。

## 昇腾比赛：换了设备，麻烦不止是环境

公司这段工作之后，我参加过华为比赛，尝试在昇腾 NPU 上训练。用的是面向 PyTorch 的适配环境，不是把这个经历改写成 MindSpore 开发。

当时 YOLO 与那套 PyTorch 版本、算子支持之间有兼容问题，出现了几处错误。我排查时怀疑某个矩阵计算相关函数有问题，但没有保留能独立复现的报错和最小例子，具体原因现在不能说死。后来我们换用 YOLOv5 的模板，在昇腾服务器上做训练。

我的体验是：迁移比预期麻烦，训练也慢。原本想把时间花在模型上，结果要先花不少时间处理兼容性。至少对我当时那套环境而言，确实不好用。至于慢在哪里、是不是某个算子的实现出了问题，要拿回当时的版本和日志才能判断，不能把一次经历扩展成所有昇腾环境的结论。

现在的[昇腾 PyTorch 适配文档](https://www.hiascend.com/document/detail/zh/Pytorch/2600/index/index.html)能帮助解释这层软件栈，官方 [ModelZoo](https://github.com/ascend/modelzoo)也有模型适配入口；这些是今天可查的资料，不代表当年用了当前版本。

如果重做，我会先用目标平台已经适配的模型跑通少量训练，核对输入、loss 和参数更新，再逐步加回自己的改动。怀疑矩阵算子时，先提取一个独立的小输入比较两端结果，比抱着整套 YOLO 一起调更容易定位。

现在有 AI 帮忙，整理实验配置、解释报错、写测速脚本和检查导出链路，都可以少做一些重复劳动。但模型为什么改、标注哪些对象、比较什么指标，仍需要我先想清楚。经历过训练一天、截图几毫秒和换平台跑不通之后，我更愿意先把这些问题写明白，再开始下一轮。
