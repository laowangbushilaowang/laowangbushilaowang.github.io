本科做 NLP 项目时，我参与搭建了一个心理健康问答机器人：从公开咨询网站收集问题与回答，训练问题分类器，再比较从零训练的 Transformer 与微调后的 DialoGPT，最后接到一个 Django 网页上。

模型能输出句子，网页也能发送问题。但一条测试回答把这件事的难点暴露得很清楚。

用户问的是：和父母没法沟通，对方总觉得自己没有权利做任何事。DialoGPT 的回答却以“很遗憾听到你的父母去世”开始，随后继续给出听起来很正式的建议。

句子通顺，语气关切，事情却理解错了。这个项目最值得回顾的，正是我们怎样从“训练一个能回答的模型”，走到“判断它到底有没有回答对”。

## 先把问题、主题和回答收集起来

我们用 Python 的 Requests 和 BeautifulSoup 收集 CounselChat 上的咨询问答。一个样本不只有两段文字，还包含问题标题和主题标签。标题适合做词频分析，标签用于问题分类，问题与回答则组成生成模型的训练对。

整个项目分成四步：

1. **采集与清洗**：得到问题、回答和主题，过滤不适合训练的文本。
2. **问题分类**：用双向 LSTM 判断问题属于哪个主题。
3. **回答生成**：比较自建 Transformer 与预训练的 DialoGPT。
4. **回答评估与网页演示**：计算文本指标，再请人阅读回答、打分。

分类与生成是两个任务。判断一个问题涉及焦虑，并不意味着已经知道该怎样回答；我们分别评估它们，不能拿分类准确率证明聊天质量。

![问题和标题中的高频二元词组](/images/chatbot/question-bigrams.webp)

图里的两个词连在一起统计，比单个词稍多一层上下文。但词频只能帮助认识语料，不能据此判断提问者的健康状态。

清洗后保留了 **1,734 个问答样本**。当时的过滤规则包括：去掉带 URL 的样本、同一词重复超过三次的文本，以及少于 5 词或超过 350 词的回答。分类预处理还做了词形还原和停用词处理；一个问题有多个主题时，取第一个主题作为标签。

这些规则让数据更容易送进模型，也损失了一些信息。多主题问题被压成单标签，是一种简化；重复表达可能是网页噪声，也可能是提问本身的一部分。清洗规则不能只看它删掉了多少行，还要看它删掉了什么。分类与生成需要的信息不同，同一套清洗也未必都适合。

## 分类器的 99%，为什么不能算成功

问题分类采用双向 LSTM，用正向与反向的序列信息形成文本表示，再输出主题类别。训练采用 70% / 30% 的训练—验证划分，batch size 为 128，训练 32 个 epoch。

| 指标 | 结果 |
| --- | ---: |
| 训练准确率 | 99% |
| 验证准确率 | 71% |
| 最终训练 loss | 0.01 |

![LSTM 分类器的训练与验证准确率](/images/chatbot/classification-accuracy.webp)

曲线里，训练准确率继续往上走，验证准确率较早进入平台。这说明模型在训练样本上学得很好，但有明显的泛化差距；单看 99%，会把结论看反。

这里还有标签的难处：咨询问题经常横跨家庭、关系和焦虑，取第一个主题不一定代表唯一正确答案。分类误差需要结合错误样例判断，不能全部解释成模型太小，也不能用主题重叠替模型开脱。原图中标为 `test` 的曲线，在报告中对应验证集；这里按报告的划分称为验证准确率。

## 从零训练，还是用已经会说话的模型

我们走了两条路线。第一条是搭建标准的编码器—解码器 Transformer，实现注意力、位置编码和 mask；第二条是用 DialoGPT 的预训练权重，在咨询问答上微调。

| 路线 | 实现重点 | 要面对的问题 |
| --- | --- | --- |
| 自建 Transformer | 编码问题，逐词生成回答；处理 padding 和解码时的未来词屏蔽 | 小语料既要教语言表达，也要教问答对应关系 |
| DialoGPT 微调 | 使用基于 GPT-2 的对话模型，调整到咨询问答语料 | 已有对话能力，不等于理解咨询场景 |

位置编码告诉模型词的顺序；padding mask 让补齐长度的空位不参与有效注意力；解码 mask 则阻止训练时偷看后面的答案。它们是让训练任务成立的基础，不是额外加上的装饰。

![自建 Transformer 的训练 loss 与 accuracy](/images/chatbot/transformer-training.webp)

这是自建模型的训练曲线，不能拿其中的 accuracy 与 LSTM 的主题分类准确率比较。生成任务预测的是输出序列，分类任务预测的是主题标签。

DialoGPT 使用 **345M 参数**的版本，通过 Hugging Face Transformers 和 PyTorch 进行微调。报告记录了 1,145 个训练样本，以及 Colab 的 V100、Kaggle 的 T4 计算环境。1,145 是这部分的训练样本数，不能与清洗后的 1,734 混成一个数据规模。[DialoGPT 原项目](https://github.com/microsoft/DialoGPT)

预训练减少了从零学习语言的负担，但没有消除小样本的问题。咨询主题分得多，每类能提供的回答有限；常见的安慰句容易学，准确理解一个具体处境难得多。

## 自动指标和读者的评价，指向了不同的东西

我们先计算回答与参考答案的文本匹配指标。

| 自动指标 | 自建 Transformer | DialoGPT |
| --- | ---: | ---: |
| BLEU | 0.0452 | 0.0469 |
| ROUGE | 0.0694 | 0.0382 |
| METEOR | 0.0281 | 0.0264 |

DialoGPT 的 BLEU 略高，另外两项更低，谈不上全面胜出。这些是当时评估的输出，具体实现与 ROUGE 变体没有完整记录，不适合跨项目比较。

问答也不像一道只有标准句子的填空题。两段意思相近的回答可以用完全不同的词；反过来，重复“我理解你的处境”，可能碰巧与参考答案重合，却没有解决问题。因此我们另做了问卷：提供 **20 个问题及对应回答**，请参与者按五个维度以 0–10 分评分，得到 **37 份有效反馈**。

| 人工评分维度 | 自建 Transformer | DialoGPT |
| --- | ---: | ---: |
| 整体质量 | 5.932 | 7.392 |
| 多样性 | 4.510 | 5.389 |
| 一致性 | 4.107 | 4.736 |
| 流畅性 | 5.381 | 5.483 |
| 适切性 | **4.193** | **3.038** |

DialoGPT 在前四项的平均分更高，适切性却更低。这里的“适切性”，是回答的语气、内容和表达是否适合这个问题与读者。它不是医学效果评分，37 份反馈也不能证明模型能提供有效治疗。

开头那个错误就说明了两种能力的区别。自建 Transformer 的回答很笼统，大意是可以表达悲伤或脆弱；DialoGPT 写得更完整，却引入了父母去世这个并不存在的前提。更长、更像人说的话，并不保证更贴合问题。这个例子与适切性评分提醒的是同一类问题，但不能仅凭一个例子解释整个分数差异。

## 接上网页以后，项目完成了哪一步

我们用 Django 做了输入框与发送按钮，让模型通过网页接受问题并返回回答。

![Django 聊天网页的输入界面](/images/chatbot/web-interface.webp)

界面完成了演示入口，却没有替模型补上理解能力。系统也没有可靠记住之前的交流，连续对话时可能忽略用户已经说明的信息。网页可用、单轮输出可读、长期对话有帮助，是三个不同的验收问题。

这次项目把数据采集、分类、训练、微调、评估和网页连接在一起，也留下了一个很具体的教训：**做生成模型，不能在 loss 下降、句子通顺的时候就收工。要回到输入，看回答是否保留了问题的事实，是否真正回应了问题。**

对这个原型，最诚实的结论是：我们跑通了两条生成路线，也看见了预训练带来的表达收益，但回答的适切性仍然不足。这个差距本身，就是值得留下的实验结果。
