2021 年的数据库课程项目，我做了一个球鞋交易网站。选球鞋是因为自己喜欢，做网站则是想让数据库里那些表真的派上用场：能找鞋、能上架，买完以后还能查订单。

项目是我一个人完成的。爬虫自己写，数据库自己设计，后端用 Django。前端当时不懂，就找现成的商店模板，一点一点改。按我现在的回忆，做到最后只剩支付还没接，网站的主要功能已经搭得差不多了。

一个人做的难处是，每部分最后都得接到一起。商品抓下来了，要能放进数据库；数据库有记录了，要能出现在页面上；按钮点下去，还得改变对应的库存、留下订单。下面就沿着这条路，讲当时具体怎么做。

*配图用原仓库模板、样式和保存的商品资料重制；不是 2021 年的运行截图。商品照片沿用项目保存的来源站素材。*

## 手写爬虫，让浏览器替我加载商品

网站首先要有鞋。我的爬虫采集 Sneaker Con 的商品目录，把名称、价格、品牌、商品编号和图片链接提取出来。

这里用的是 Selenium 模拟浏览器操作。保存的代码调用 Edge，打开目录页，等待 `Load More` 按钮出现，再点击它，让更多商品加载到页面上。等这些操作结束，取出浏览器中的 HTML，用 BeautifulSoup 找商品卡片、读字段，最后保存成 CSV。

所以它可以分成两步：先让浏览器把内容加载出来，再从已经得到的页面里提取数据。整个采集过程是这样：

```text
Sneaker Con 商品页
  → Selenium 打开浏览器、点击 Load More
  → BeautifulSoup 读取商品卡片
  → CSV + 下载的商品图片
  → 导入 MySQL
  → 自己的网站查询和展示
```

手写这段程序，需要自己认清页面结构：商品卡片在哪里，名称和价格分别在哪个标签里，某条商品缺了字段怎么办。保存的版本把缺失价格、品牌留空，图片提取也有比较粗的选择条件。今天再写，我会先对照页面抽查一批商品，确认字段没有抓错，再扩大采集范围。

我把采集和网站查询分开了。商品先落成文件，再导入数据库，页面读自己的商品表。这样每次访问目录时都不用重新抓来源站，也能单独检查采集出的数据。现存仓库保存了 7,084 条商品记录。

## 数据库要区分鞋款、谁在卖、谁买了

这是数据库课程项目里最值得展开的部分。页面看起来都在显示“鞋”，但同一个词在不同操作里指的东西不一样。

比如，两位卖家都有同一款 Jordan。鞋款名称、品牌和图片可以共用，但卖家的库存要分别记录。买家买走其中一份库存，另一位卖家仍然可以卖；目录里这款鞋也不该一起消失。

我把这些关系拆成几张表：

| 表 | 在网站里负责什么 |
| --- | --- |
| `sneaker` | 鞋款资料：名称、品牌、价格、图片 |
| `seller` / `buyer` | 卖家和买家账号 |
| `inventory` | 一份在售库存，关联鞋款和卖家 |
| `sold` | 已售记录，保存原库存编号和鞋款关系 |
| `order` | 买家、卖家、已售记录、日期及可选定制项 |
| `customization` | 演示用的颜色定制项 |

看一次上架就容易理解：卖家选已有鞋款，程序新增一条库存记录，把它连到这位卖家。它不需要重新复制一份鞋款名称和图片。详情页再统计这个鞋款关联了多少条库存，显示可售数量。

```text
鞋款 sneaker ← 在售库存 inventory → 卖家 seller

买家 buyer → 订单 order → 已售记录 sold → 鞋款 sneaker
                  ├──→ 卖家 seller
                  └──→ 定制项 customization（可选）
```

*按保存的模型整理的关系示意；在售库存与已售记录是不同的表。*

![原项目详情模板重制：商品资料与库存数量分别显示](/images/sneaker/detail-reconstruction.webp "原模板重制。Inventory: 3 为示例值，Buy 已禁用；用于说明商品资料与库存的区别。")

购买处理则把在售库存转成已售记录，再让订单引用它。这样库存退出在售列表后，订单还可以沿着关系查回买过的鞋，以及当时的买家和卖家。这是当时设计 `sold` 表的作用。

模型当然还有课程项目的简化：库存没有尺码、成色和卖家自己的报价，价格放在鞋款表里。今天重做，我会把这些字段放到具体的在售商品上。先分清“哪种鞋”和“哪一份出售物”，后面才有位置补这些属性。

## 用 Django 的数据库接口，把表接到页面

后端主要用 Django 自带的 ORM，也就是把数据库记录当作 Python 对象来操作的接口。表结构定义在 `models.py`，页面请求的处理写在 `views.py`，查询结果再交给模板。

我用 `get()` 取一条商品，用 `filter()` 找符合条件的商品或库存，用 `create()` 新增记录，再用 `count()` 统计数量。下面两行摘自原项目，分别用在搜索和商品详情里：

```python
s = sneaker.objects.filter(name__icontains=key)
inv = inventory.objects.filter(sneakerid=id).count()
```

第一行按名称做包含查询，第二行数出某个鞋款的库存。Django 负责把这些调用转换成数据库查询，我在视图里处理搜索词、商品编号以及页面需要哪些结果。对这些接口的说明可参见 [Django 查询文档](https://docs.djangoproject.com/en/5.2/topics/db/queries/)。

ORM 省去了在每个页面里拼 SQL 的工作，但表之间怎么关联，仍然要自己想清楚。商品详情查的是鞋款和库存；订单页查的是买家或卖家的订单，再找到鞋款和定制颜色。表设计如果混在一起，换成 Python 接口也不会自动变清楚。

搜索和分页也是这样接出来的。后端先按名称、品牌筛选，每页放 12 条；模板负责显示商品卡片和翻页链接。下一页链接要带上原来的查询条件，否则翻页以后就会回到全站商品。这些小地方决定了页面能不能连贯地用下去。

## 不会做前端，就从模板一点点改

当时我不会从零做前端，先用了现成的 Bootstrap 商店模板。它给了我导航栏、商品卡片和页面布局，我再逐页把自己的数据和操作填进去。

原模板里的卡片循环改成遍历 Django 传来的商品：标题放鞋名，图片路径读商品字段，点击卡片跳到对应的详情页。侧栏遍历品牌，分页链接接上页码和筛选条件。模板里的 `{{ obj.name }}`、`{{ obj.price }}` 就是后端数据出现在页面上的位置。

详情页还要显示库存，卖家页面要能上架、查看自己的库存，买家和卖家则各自查订单。前端每增加一个入口，后端都得有相应的查询或写入，数据库里也得有地方保存它。

这也是模板帮我的地方：先有一个看得见的页面，我就能对着它处理每块内容。哪些字段需要传过去，哪个按钮应该提交表单，链接要带什么商品编号，都变成了可以逐项解决的具体问题。视觉布局借用了模板，把页面接到自己设计的数据和功能上则是我做的工作。

## 最后没接上的支付

按我对当时进度的回忆，账号、商品目录、库存、买卖操作和订单这些主要部分已经做得差不多，剩下支付没有接。因此网站里的购买是在模拟库存与订单变化，没有真的收款。

这次回看代码，也能看到购买处理还需要整理：订单写入在它引用的已售记录之前，多次写入没有放进同一个数据库事务。这是今天检查旧实现发现的问题；没有重新跑通旧购买流程。真正继续做支付前，我会先把这一段的一致性处理好，再区分待支付、付款成功和取消这些状态。

我现在记得最清楚的，还是一个人把这几块搭起来的过程。不会做页面，就从模板改；商品数据自己采；表之间的关系自己设计，再用 Django 把它们接到搜索、上架和订单里。数据库课程里的表，最后成了一个可以操作的网站。支付停在那里，留下了一件当时没做完的事。
