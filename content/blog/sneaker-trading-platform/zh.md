2021 年做数据库课程项目时，我选了自己感兴趣的球鞋。题目很容易想象：买家找鞋、卖家上架，网站展示商品，购买后能查到订单。真正动手以后，这几个动作需要对应到具体的数据关系。

我用 Python 采集商品信息，用 MySQL 保存数据，再用 Django 做搜索、品牌筛选、买卖方账号、库存和订单页面。它是一个课程交易原型，购买操作模拟库存与订单的变化，没有接入支付。

这篇回顾主要讲两件事：怎么把网页上的商品变成自己能查询的数据；怎么区分“这是什么鞋”和“谁有一双鞋可以卖”。最后再看购买操作，以及今天重做时我会改什么。

*封面用原仓库的 Django 模板、Bootstrap 样式和商品记录重新渲染，不是当年的运行截图。商品图片来自项目保存的来源站素材。*

## 把商品目录搬进网站

爬虫采集的是 Sneaker Con 的商品目录。页面通过 `Load More` 加载更多商品，我用 Selenium 操作浏览器，再把加载后的 HTML 交给 BeautifulSoup，提取名称、价格、品牌、商品编号和图片链接，最后写成 CSV。

这条链路很直接：

```text
来源商品页面
  → Selenium 加载更多内容
  → BeautifulSoup 提取商品字段
  → CSV 与图片文件
  → MySQL 商品表
  → Django 搜索与展示
```

浏览器处理网页交互，解析器处理已经得到的内容。导入脚本再把字段写入数据库，下载有图片链接的商品图，为没有图片的记录设置占位图。前端读取商品表，不必在每次打开页面时重新访问来源站。

这里也有当时处理得比较粗的地方。保存下来的爬虫把缺失价格、品牌留空，图片提取还用了特定的 `alt` 值；导入脚本里一行价格补缺没有接住返回值。抓到一张表以后，空值究竟怎样影响展示，需要逐字段检查。今天再做，我会先抽查几页结果，记录每个字段的缺失情况，再扩大采集范围。

简历曾写累计采集 20,000+ 条球鞋信息。这次回看，仓库保留下来的商品 CSV 是 **7,084 条、名称不重复的记录**，同目录没有足够材料还原累计采集与筛选过程。下面的回顾以保存下来的版本为准，不把两个数字混成一个。

### 搜索、筛选与翻页一起工作

有了数据，页面不能只负责展示第一页。用户搜索一个词、选好品牌，再点击下一页，应该仍然看同一组结果。

目录视图先按名称做包含查询，再按品牌筛选，用 Django 的分页器每页显示 12 条。模板把搜索词和品牌继续放进下一页链接。例如下面是解释这个行为的示例地址：

```text
/sneaker/library?searchkey=Jordan&brand=Jordan&page=2
```

`page=2` 改变的是同一组查询结果中的位置。筛选条件没有跟过去，用户点了下一页就会回到全站商品。这是小功能，但它把数据库查询和用户正在做的事连接了起来。

页面布局沿用了现成的 Bootstrap 商店模板。我把商品、品牌和分页结果接进模板，重点放在数据与功能；没有把模板样式当成自己的原创设计。

## 鞋款、库存和订单怎么分

商品表能回答“这是什么鞋”，却回答不了“谁能卖给我”。同一鞋款可以有多个卖家，也可以有多份库存。把卖家直接写在商品行上，后面会很难表示这些关系。

我把它们拆进不同的表。原项目中的命名比较朴素：

| 表 | 保存什么 |
| --- | --- |
| `sneaker` | 鞋款名称、品牌、价格和图片 |
| `seller` / `buyer` | 卖方和买方账号 |
| `inventory` | 一条在售库存，对应鞋款和卖家 |
| `sold` | 已售记录，保留原库存编号及鞋款关系 |
| `order` | 买家、卖家、成交记录、日期和可选定制项 |
| `customization` | 演示用的颜色定制选项 |

举个简化例子：两位卖家都卖同一鞋款，商品资料可以共用，库存分别记录卖家。卖掉其中一条库存，商品本身不应该从目录里消失，另一位卖家的库存也不应该受影响。这个例子说明表之间的关系，不代表项目有过这样的真实交易。

详情页通过统计该鞋款的库存记录，显示还有多少条在售库存。卖家上架时，也是给已有鞋款增加库存记录，而不是再复制一套商品资料。

![原项目详情模板重制：商品资料与库存数量分别显示](/images/sneaker/detail-reconstruction.webp "原模板与保存的商品记录重新渲染。Inventory: 3 是说明用的值，Buy 已禁用；不代表真实库存或完成过购买测试。")

回看这个模型，我也能看到它省略了什么。库存没有尺码、成色或卖家自己的报价，价格放在鞋款表里。因此它能够演示鞋款、卖家和库存的关联，却还不能充分表达真实的二手球鞋交易。今天再设计，我会把这些描述具体出售物的字段放到在售记录里。

## 模拟购买怎样留下完整的订单

买家点击购买后，页面上的库存会少一条。但订单页面还要能回答：买了什么、向谁买、何时买，以及选了什么定制项。

旧实现用 `sold` 表保留已售关系：订单连接买家与卖家，并通过成交记录找回鞋款；原来的在售库存随后删除。查询订单时，程序沿这些关系取出商品名和定制颜色，再交给页面展示。

“从在售列表移走”和“保留交易历史”在这里有不同的目的。只删库存而没有留下关系，订单以后就找不到买过的鞋；只留库存不改变状态，又会继续显示为可售。

不过，**这段购买代码今天重看，需要先修操作顺序和一致性**。它先创建订单，再创建订单要引用的已售记录，最后删除库存；这些写入没有放在同一个事务中。模型里的订单外键指向 `sold`，创建顺序应该与这个依赖相符。我这次只核对了源码，没有把旧购买流程跑通，因此不把它描述为验证过的交易系统。

再用一个假设检查设计：最后一条库存同时被两位买家看到，两次请求都读到“还有货”，接下来怎样避免都拿走同一条库存？页面上的库存数字解决不了这个问题，后台需要在同一次数据库事务中确认可售状态、建立成交与订单记录、更新库存；重复请求也不能再创建一份订单。

如果重做，我会保留在售记录，用状态表达已售，并在订单里保存成交时的商品说明与价格。这样以后卖家改了商品资料，旧订单仍然说得清当时买的是什么。账号认证、卖家权限检查和价格字段类型也需要重新处理，不能只靠页面隐藏按钮。

这个项目把爬虫、数据库和网页接在了一起。现在最值得继续用的，是先弄清楚一个动作涉及哪些对象：浏览看商品，出售占用库存，购买改变状态，订单保留过去的信息。下一次再做交易类应用，我会先用这些具体动作检查数据模型，再往页面里填功能。
