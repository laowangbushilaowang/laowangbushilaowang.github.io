最初，我做的是一个本地订阅管理工具：在网页里准备资料，调用脚本，打开浏览器，再查询结果。单项功能有了，操作起来仍然要在几个页面之间来回跳。

后来加上订单后台，问题更明显了。后台知道正在处理哪一单，执行页面却还要重新填资料；脚本可能已经结束，页面上的进度还是上一轮。要完成一次任务，我得自己把这些地方对起来。

我想把它们接成一套自己用着顺手的工作台：从订单进入任务，看到正在做什么，遇到问题能停下来，最后回读结果、归档。早期我参考过开源的 [chatgpt-specimen-toolbox](https://github.com/1837620622/chatgpt-specimen-toolbox)；工作流、布局和故障反馈由我提出，Codex 协助实现与检查。这里讲其中通用的工程设计。

## 先把一次任务接完整

我提过一个很具体的要求：从后台开始，到最后归档，能不能少复制几次、少找几个页面？

例如，已经在后台选中了订单，进入执行页时就应该带上它的上下文；常用内容应该能直接复制；查询、执行和归档各自有入口。每个按钮单独可用还不够，前一步的结果得能交给下一步。

这套工作台的操作关系可以概括成四步：

1. **选择订单**：确定当前任务和所需资料。
2. **检查与执行**：先查现状，再启动对应操作。
3. **查看进度与结果**：执行到哪一步、哪里失败，直接显示在当前任务旁边。
4. **处理收尾**：回读外部状态，按需要归档；人工处理有独立入口。

网页负责选择和展示，后端保存记录，本机执行器运行脚本或浏览器。页面发出一次请求后，后面可能还要等很久，所以我把进度放在订单右边，让它跟着执行更新。

```text
网页：选择任务、发起操作、查看进度
                ↓
后端：订单记录与任务状态
                ↓
本机执行器：脚本 / 浏览器
                ↓
查询实际结果 → 更新当前任务 → 按需归档
```

*上面是工作台的职责概览。具体业务步骤没有展开。*

这里最有用的改动，是让“现在处理哪一单”贯穿整段操作。只要还要靠人记住上一步属于谁，几个页面就还没有接好。

## 进度要能解释失败

只有一个转圈图标时，等十秒和等一分钟看起来一样。我关心的是它在等什么：本机任务没启动，外部请求没有返回，还是最后查询失败了？

因此，我要求每个阶段显示自己的状态和错误。当前订单、执行进度放在相邻的位置；重新查询失败，也要在查询结果区说明，不能点完没有动静。

![工作台的当前订单与分阶段进度](/images/projects/private-workbench/query-replay.webp)

*实际界面组件的测试数据重放。订单、时间和 HTTP 503 均为合成测试值；所有写操作关闭。图中第一阶段失败，后续阶段保持待处理。*

图里左边是查询结果，右边是分阶段进度。这样排，能直接看出当前失败在哪里、后面哪些还没有执行。详细错误留在工作台里，面向外部的页面只需要提供必要的状态。

还有一种更容易误导人的情况：本次查询失败，后台刷新却把上次成功的记录又填了回来。旧结果可以保留，但它必须仍然是旧结果。本次查询失败的提示要留下，不能被自动刷新擦掉。

我也保留了人工处理入口。有时我会在网页之外完成某项操作，再回来核对和更新记录。于是“管理员设为成功”和“程序查询确认完成”需要分清，不能见到数据库里的 `success` 就当作所有步骤都自动跑过了。

## 重试和停止，都得知道自己在处理哪一次

第二次运行时，上一轮亮着的进度还留在屏幕上，这是我反复反馈过的问题。同一笔订单可以运行多次，订单编号并不能说明眼前这些进度属于哪一次。

实现里用了三种标识，各自管一件事：

| 变化 | 怎样区分 | 防止什么 |
|---|---|---|
| 从订单 A 切到 B | 页面选择版本 | A 的迟到响应填进 B |
| 同一订单重新执行 | 本次执行 ID | 上一轮完成记录点亮这一轮进度 |
| 手动发起新查询 | 查询序号 | 较早的轮询覆盖这次查询 |

不必让使用者看到这些编号，但界面得靠它们决定哪些结果还能显示。重新开始后，进度跟随本次执行；晚到的旧响应不能替新任务宣布完成。

我还要求所有对外按钮限制重复请求。同一页面里，进行中的相同读取可以共享；会修改状态的操作则拒绝并发重复点击。这解决页面内的重叠请求，多标签页或多进程的重复提交仍需要后端另外处理。

停止也放在原来的按钮上：开始后，按钮变成“停止”，不用再去页面角落找它。点击后，网页结束等待，同时请求本机执行器终止对应任务；收到停止回执前，控件保持忙碌，避免上一轮还没退干净就启动下一轮。

**停止本机任务，无法撤回外部系统已经收到的请求。** 如果回执没收到，页面就说明进程退出尚未确认。下一步先查原记录，不能把连接断了理解成什么都没发生。

这些情况适合单独做测试：让旧响应晚一点返回、在任务启动前后分别取消、确认停止不会影响另一项任务。它们比只看一遍顺利完成的流程更能暴露界面问题。

## 工具长大以后，目录也要跟着整理

功能陆续加进来，我还要求整理目录、用 Git 管版本，并把约定写进 `AGENTS.md`。否则下一次让 Codex 修改时，得先猜哪个入口还在用、哪些只是早期试验。

主项目中，几类文件有明确的位置：

```text
app.py                     本地 Web 与后端入口
chrome_checkout_runner.mjs 浏览器执行器
web/                       网页与订单后台
config/                    可以提交的配置示例
runtime/                   会话、运行状态、调试文件
business_records/          账本与凭证
archive/                   旧原型和调试产物
```

运行资料、业务记录和旧调试产物各自存放，排除在 Git 之外。源码更新时保留这些资料；回退代码也不等于把新增记录一起回退。配置示例可以跟代码走，真实配置留在运行环境里。

这套工作台目前仍是私有工具，浏览器交互和外部接口还需要维护。我没有把这次代码复查当作当前线上全流程验收，也没有统计自动完成率。对我来说，它的用途已经很具体：打开一项任务，就能找到资料、执行入口和结果，不必再靠几个网页加记忆把流程拼起来。
