查询失败后，上一份结果可以留在屏幕上，但它得明确是旧记录。如果页面刚报错，后台刷新又把旧数据写成“当前状态”，使用者会以为这次查询成功了。请求没有修好，界面倒先替它宣布了胜利。

我的本地工作台把订单、账号查询、浏览器执行和收据管理放在一处，供自己处理订阅相关任务。做它时，我提出过很具体的要求：错误要跟着步骤显示；所有对外操作都要限制重复点击；运行中的按钮再点一次，就能停止。这些要求最后牵出了同一个问题：页面、执行器和外部系统各有自己的时间，谁能决定屏幕上现在显示什么？

开发由我通过 Codex 推进，需求、界面取舍和故障反馈来自实际使用，代码实现与检查由 Codex 协助完成。本文只展开通用工程设计。

## “停止”要停到哪一层

一个按钮发出请求后，可能有三件事同时进行：浏览器在等响应，本机子进程在跑，外部系统在处理已收到的请求。

点停止能让浏览器结束等待。`AbortController` 可以中止 fetch、响应体读取等支持它的操作，具体范围见 [MDN 文档](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort)。服务器收到之前那条请求后做了什么，还需要另外查。

所以我的工作台会同时做两件事：中止当前页面操作，并用独立请求通知本机执行器停止。取消请求必须有自己的 `AbortController`；沿用刚被中止的 signal，它连门都出不去。

本机执行器按 `operation_id` 查找这次任务。取消标记和进程登记由同一把锁保护：标记先到，后续步骤就不能启动；子进程已经启动，先向本应用创建的进程组发 `SIGTERM`，等不到退出再发 `SIGKILL`，最后检查它是否真的退出。其他任务的进程不在这次取消范围里。

页面在等取消回执时仍保持忙碌，避免旧任务尚未确认退出，新任务已经出发。回执没回来，界面只能说“已停止页面等待，本机任务终止状态未确认”。这句话不漂亮，却比一个假的绿色对勾实用。

外部请求如果已经发出，停止本机进程也无法把它收回来。下一步应读取原记录，确认结果，再决定是否重试。尤其是会修改外部状态的操作，不能拿一次连接中断当作“什么都没发生”。

## 同一个读取，共享一次等待

工作台会自动刷新进度，前台操作结束后也要再读一次详情。它们很容易撞上同一个 URL。

我采用的办法是把正在进行的 GET 放进一个 Map：方法和 URL 相同，返回同一个 Promise；完成后移除。后一位调用者一起等结果。POST 则用另一份集合记录，同一个 key 还在处理时拒绝第二次点击。

这解决的是一个页面内的请求重叠。它没有把响应长期缓存下来，也不能保证另一个标签页、另一个进程不会重复提交。请求 key 只有方法和 URL，若将来接口允许同一 URL 携带不同参数或权限，就需要重新考虑合并条件。

共享读取还有一个容易漏掉的细节：前台已经停止，后台那次读取可能仍有人要用。

假设后台先开始读详情，随后前台加入等待。前台取消时，可以解除自己的等待，让原 Promise 继续给后台提供结果。下面是项目里这层包装的逻辑，去掉了外围调用代码：

```javascript
function awaitOperation(value, signal) {
  const pending = Promise.resolve(value);
  if (!signal) return pending;

  return new Promise((resolve, reject) => {
    let finished = false;
    const finish = (settle, result) => {
      if (finished) return;
      finished = true;
      signal.removeEventListener('abort', abort);
      settle(result);
    };
    const abort = () => finish(reject, signal.reason);
    pending.then(
      result => finish(resolve, result),
      error => finish(reject, error)
    );
    if (signal.aborted) abort();
    else signal.addEventListener('abort', abort, { once: true });
  });
}
```

这段代码没有中止底层读取。它结束当前调用者的等待，并清掉自己的监听器；即使原 Promise 稍后失败，失败也有人接住。执行包装还会在等待前后检查 signal，阻止下一步操作继续发送。

这里有一个条件：底层读取最初没有绑定这次前台取消信号。如果它本来就由当前操作发起，并绑定了该 signal，底层 fetch 也会被中止。共享 Promise 并不会自动改变请求的归属。

## 旧响应还会回来，但不能随便画上去

网络允许响应乱序，页面得自己记得正在看谁。

用户选了订单 A，详情还没读完，又切到 B。A 的响应回来时，取消请求未必来得及生效；把它写进 B 的卡片就错了。工作台为当前选择保留 `generation`，切换时递增。读取开始时记下这一版，返回时再比较，版本不符就不渲染。

项目里另外两种标识解决的是不同问题：

| 标识 | 对应的变化 | 防止什么 |
|---|---|---|
| `generation` | 当前选中的订单变了 | A 的详情落到 B 的界面 |
| `operation_id` | 同一订单开始了一次新执行 | 上一次执行的进度冒充本次进度 |
| `querySeq` | 用户发起了一次明确查询 | 较早开始的轮询盖过这次查询 |

只比较订单号还不够。同一订单可以连续处理多次：旧执行已完成，新执行刚启动。界面若拿旧的“已完成”填进新进度，六个步骤会瞬间变绿，实际新任务还在第一步。

因此活动执行优先读取与本次 `operation_id` 匹配的事件，旧的完成记录留在历史里。显式查询也有自己的序号，进度刷新可以更新进度，但不能顺手替换正在查询的那块结果。

这些标识各有作用。页面版本管渲染，执行标识管任务归属，它们都不能证明外部操作已经完成。

左边显示查询失败，右边显示具体卡在哪一步，以及后续步骤还没有执行。错误码和 HTTP 状态分别显示；没有 HTTP 状态的本机错误，也能保留自己的诊断信息。

我在使用反馈里要求把错误直接放到步骤下方，因为一个笼统的“失败”不足以决定接下来做什么。准备资料失败、请求已发出但结果未知、最终状态读取失败，恢复方式各不相同。后两种尤其需要保留原执行记录。

快照也有同样的问题。最近一次查询失败后，自动进度刷新不能用更早保存的状态把错误擦掉。工作台保留本次查询错误，等新的查询成功、换了凭据或切换订单，再按相应路径清理它。

这里还有一条我在复查中需要特别区分的路径：管理员可以手动把订单设为成功。因此数据库里的 `success` 不能单独证明自动执行已经核验完成。界面保留人工处理入口，分析运行结果时则要同时看来源和验证记录。

## 自动刷新别抢走手里的操作

轮询频率只解决多久问一次，没解决什么时候不该问。

当前代码里，列表每五秒检查一次；工作台定时器每 1.5 秒触发，空闲时又限制为至少十秒一次。页面隐藏、面板关闭、已有刷新进行、正在显式查询等条件，会让它跳过这一轮。列表数据没有变化，就不重画；临时连接失败保留现有列表，登录失效则清理私有视图。

这些选择让刷新围着当前操作走。它们没有经过完整的延迟或服务器负载对照，不能据此说性能提高了多少。

测试倒可以把几个难碰的时序摆出来：停止后才返回的读请求不能触发下一次写；取消请求未确认时不能解锁；旧执行进度不能盖过新执行；最新查询失败不能被旧快照抹掉。本机测试还启动一个临时 sleep 子进程，确认取消能让它退出，并检查不会误停另一任务。这些回归检查在本次复查中通过。

复查也发现了测试自身的脆弱处：一个尚未提交的轮询测试用字符串位置截取源码，函数已经换了名字、定时器移到文件尾，它的四个管理端用例就没能注册定时器而失败。不能把这种失败直接说成产品轮询坏了，也不能绕开它宣称全套通过。若继续维护，先把这些异步逻辑提取成可直接导入的模块，会比反复修截取位置可靠。

## 进程重启以后

现在本机进程注册表和取消标记还在内存里。它们能控制这次运行，进程重启后的恢复需要另做持久化设计。浏览器里禁止重复点击，也不能代替服务端幂等。

如果重做这一层，我会把执行记录和外部操作结果拆开存：一次执行有自己的起止、取消和超时；外部操作有独立的请求标识与回读结果。重启后先处理结果未知的记录，再允许新执行；取消标记则需要有明确的保留期限。随后补多标签页和重启后的测试。

这次复查没有做真实付款或云端端到端验收。下一轮我想先补重启场景：任务已经发出请求，页面关闭、执行器重启，再回来时怎样找到原记录。这个场景还不能只靠浏览器里的几个标识解决。
