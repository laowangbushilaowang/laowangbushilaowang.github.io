长期项目的上下文问题，常常出在信息之间的关系上。代码说明实现，实验报告保存结果，可是换一个会话继续做，Agent 还需要判断：现在跟进哪项任务？哪份结果仍然有效？眼前这条规则适用于哪个项目？

我现在用文件结构把这些关系写出来。项目入口负责定位任务，交接保存当前状态，交接中的链接再指向代码和结果。这样安排的用意，是让 Agent 在展开阅读前先选对材料，少从一堆历史文件里猜“我们现在做到哪里了”。

一次与 Codex 整理工作台时出现的归属问题，说明了为什么入口需要写得足够具体。

## 目录归属决定规则的适用范围

有一次整理工作台，外层项目的上下文目录被放进了嵌套的 Hermes 项目。Hermes 有自己的入口，但那份目录一度被当成外层的通用工作区。

文件照样能写，链接也可以存在。麻烦在于，下一次接手外层项目时，要到另一个独立项目里找交接；Hermes 的记录里又混进了外层任务。文件保存成功，这个任务的归属却错了。

后来把外层交接放回外层项目，Hermes 保留自己的入口。这个修正给文件结构加了一条很实际的要求：**入口要先说清项目边界。** 目录嵌套只说明存放位置，不能据此把两个项目的规则和进度合在一起。

所以我让总索引保留项目边界和入口，各项目维护各自的当前交接。总索引如果也抄一份实时进度，更新时就要同时照顾两处。漏掉一处，新会话又得判断哪份才算数。

## 把当前任务从历史里分出来

规则和进度的寿命不同。实验的比较口径可能持续几个月，本周的阻塞却会随着一次运行改变。把它们混在一个越来越长的文档里，Agent 就得先辨认每段话是哪一类、还适不适用。

我把长期要求放在 `AGENTS.md`，当前任务放在交接文件。多项持续任务可以沿用下面的结构。目录名经过缩短，业务文件省略；简单项目不需要建齐这些文件。

```text
project/
├── AGENTS.md
├── README.md
└── .context/
    ├── README.md
    └── tasks/
        └── task-id/
            ├── HANDOFF.md
            ├── APPROVED_PLAN.md
            ├── decisions.md
            ├── notes.md
            ├── state.json
            └── events.jsonl
```

`HANDOFF.md` 让接手者尽快看到当前问题。已经批准的范围留在 `APPROVED_PLAN.md`，重要决定的原因和原件入口留在 `decisions.md`。有自动观察器时，才需要它维护的 `state.json` 和 `events.jsonl`；人工跟进的问题放在 `notes.md`，避免下次自动生成时被覆盖。

当前交接随进展更新，观察日志往后追加。放弃一个方案，也保留当时的理由和结果入口。这样再遇到同类问题时，可以查清当时为什么停下来，而不必重新跑一遍才想起那个失败。

Notebook、数据和图仍放在原业务目录。上下文目录只链接到它们。复制一套结果进来，看起来方便，后面却很容易出现两张同名图、两个不同版本的“最终结果”。

## 读取路径比通读清单更有用

文件分层以后，还要让 Agent 知道什么时候读哪一层。恢复旧任务时，沿已有 README 或当前主线入口找到交接，再读取下一步依赖的代码、实验或报告。如果要追问一个决定的原因，才往历史里查。

这个顺序让目录变成了可用的上下文入口：先定位，后展开。一个明确的 UI 修改通常只需要相关组件；研究任务接手则需要当前实验身份和结果。两者读同一份全量历史，增加的内容未必能帮助这次工作。

已有项目入口保留了这样的读取条件：

```text
恢复旧任务、切换主线或背景不足时，按需读 .context/README.md；
范围明确的小修改不新增通读要求。
```

AIQuant 的根规则曾经很长，Notebook 操作和清理又有各自的细则。整理时把这些细则拆到专门文档，根文件留下触发条件和链接。修改 Notebook 时再读它的操作约定，普通源码修改沿用项目规则。根文件更适合回答“这次该去读哪里”，不必装下所有操作说明。

不过，文件在目录里，不代表新会话实际读到了它。接手后仍要核对 Agent 找到的是哪项任务、引用的是哪份结果。通过本地会话操作远端项目时，远端的规则也要读取；本地入口只能指路。

## 状态记录要说明它知道多少

交接里写“训练正常”，下一步很难据此行动。进程还在，只能说明进程存在；epoch 增加，才能支持训练在推进的判断。模型评估通过、论文图可以交付，需要另外检查。

研究任务的观察器会比较阶段、轮数、checkpoint 和任务计数，没有可测进展就留下提示。关键输入缺失或读到不完整 JSON 时，状态标成 `unverified`。它还明确保留了两个字段：

```python
'scientific_acceptance': 'not_assessed_by_observer',
'visual_acceptance': 'not_assessed_by_observer',
```

这两个值告诉下一次接手的 Agent：运行状态已经观察过，科学结论和图的验收还没有由观察器判断。交接能支持的下一步因此更明确，不会把“仍在运行”读成“已经通过”。

写入方式也影响这份状态值不值得依赖。实际观察器先追加本次记录，再替换当前状态和交接。下面节选保留原变量名，省略了摘要生成部分：

```python
with (dest / 'events.jsonl').open('a') as stream:
    stream.write(json.dumps(result, ensure_ascii=False) + '\n')
    stream.flush()
    os.fsync(stream.fileno())

atomic(state, json.dumps(result, ensure_ascii=False, indent=2) + '\n')
# text 根据同一次 result 生成
atomic(dest / 'HANDOFF.md', text)
```

先记日志，后续替换失败时仍有本次观察可以查。`atomic` 在目标目录创建临时文件，写入并 `fsync` 后，用 `os.replace` 替换单个文件；写入入口另有文件锁，避免两个观察进程同时更新。

这里还有一个没有消除的缝隙：`state.json` 和 `HANDOFF.md` 分别替换，中间可能中断。单文件原子替换没有把两份文件变成一个事务。它们不一致时，要核对观察时间，回到同次事件记录确认。目录组织再清楚，也不能替代这一步。

## Skills 保存可复用的做法

任务交接里的“下一步检查下载结果”，只属于这次工作。下载时怎样检查完整性、失败后怎样恢复，可以写进对应 Skill，供后续任务复用。这样交接保持简短，操作说明也有稳定的维护位置。

上下文初始化本身也有 Skill，后来把适用范围收窄到新项目，或入口缺失、失效时的修复。README 和交接已经能找到任务，就继续使用已有文件。每次恢复都重新初始化，会再造一套需要同步的状态。

这也是我不要求小项目照搬完整目录的原因。一份 README 和一页交接够用，就先用到它们不够用的时候。

## 交接也需要维护

文件结构提供了读取路径，但交接过期以后，Agent 仍可能沿着正确的路径读到错误的现状。重要结论要附核验时间和原件入口，下一步依赖的运行状态要重新确认。备份后的文件如果继续改过，恢复时也要比较当前版本，不能直接覆盖。

目前能核对的是这些文件怎样组织、观察器怎样写入，以及已经修正的归属问题。我还没有测量它们对接手耗时或任务成功率的影响。

我会继续沿用这套约定。新增说明前，先检查有没有文件已经承担这个用途；更新交接时，重点写下一次行动所需的事实和未解决的问题。文件越多，维护成本也越高。让下一次接手少猜一点，才值得多写这一页。
