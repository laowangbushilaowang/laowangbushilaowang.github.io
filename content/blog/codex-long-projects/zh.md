项目目录里有代码，也有昨天的结果和上个月放弃的方案。换一个 Codex 对话继续做时，我需要它先找到当前任务，再读相关材料。只把文件留下来，还没有解决接手的问题。

9 月核对上下文改造时，我问过 Codex：每个项目到底改了哪里，会不会改完反而更难用？接着问的是：“这些规则写在哪里的？”哪些文件覆盖更新，哪些一直追加，新会话又从哪里开始读？

这些问题后来变成了现在这套文件约定。它服务于我和 Codex 一起推进的研究、数据流程和个人工具。我负责提出使用要求、追问和复查，Codex 实施文件改造。下面讲文件之间怎样配合，以及整理时暴露出的几个问题。

## 文件结构：规则与任务分开

AGENTS.md 保存项目长期适用的要求：实验按什么口径比较，新文件放在哪里，哪些操作要先读专门说明。任务交接记录当前做到哪里。两种内容的更新频率不同，把它们写进同一份文件，接手时就要从长期要求里寻找最近进度。

沿用已有目录后，一个有多项持续任务的项目可以这样组织。下面缩短了目录名，省略业务文件，只展示约定中的几种文件；简单项目不需要全部创建。

```text
project/
├── AGENTS.md
├── README.md
└── .context/
    ├── README.md
    └── tasks/
        └── task-id/
            ├── HANDOFF.md
            ├── APPROVED_PLAN.md
            ├── decisions.md
            ├── notes.md
            ├── state.json
            └── events.jsonl
```

.context/README.md 帮助定位任务。HANDOFF.md 保存当前交接；已批准范围和重要决定分别留在 APPROVED_PLAN.md、decisions.md 中。需要人工跟进的问题放在 notes.md。有自动观察器时，再由它维护 state.json 和 events.jsonl。

原来的 Notebook、数据、模型和图仍在业务目录。交接给出入口，读者需要查某项结果时，再去打开原件。把它们复制进上下文目录，会多出一套需要同步的文件。

AIQuant 的根规则文件曾经很长，Notebook 操作和清理操作又各有细则。整理时把这两部分拆进专门文档，在根文件保留指针。做相关任务时再读细则，普通源码修改沿用根规则。

入口也没有要求每次通读历史。几个项目里保留的是这样一条规则：

```text
恢复旧任务、切换主线或背景不足时，按需读 .context/README.md；
范围明确的小修改不新增通读要求。
```

已有目录能用就沿用。小项目一份 README 和一页交接够用，我不想为了接手一个任务，先维护七八个空文件。

## 当前状态怎样更新

我问过状态文件会不会一直追加。这里要按用途处理：HANDOFF.md 面向下一次接手，应该尽快看到当前问题；events.jsonl 保存历次观察，需要往后追加。重要决定保留原因和出处，也不能随着下一次进度更新消失。

研究任务的观察器里，实际写入顺序是这样的。代码节选删去了生成内容的细节，变量名保持原实现：

```python
with (dest / 'events.jsonl').open('a') as stream:
    stream.write(json.dumps(result, ensure_ascii=False) + '\n')
    stream.flush()
    os.fsync(stream.fileno())

atomic(state, json.dumps(result, ensure_ascii=False, indent=2) + '\n')
# text 是根据同一次 result 生成的交接摘要
atomic(dest / 'HANDOFF.md', text)
```

先追加这次观察，再更新当前状态。如果后面的替换失败，日志里仍留有这次观察的记录。当前文件的替换函数也很短：

```python
def atomic(path, text):
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, name = tempfile.mkstemp(prefix='.' + path.name, dir=path.parent)
    try:
        with os.fdopen(fd, 'w') as stream:
            stream.write(text)
            stream.flush()
            os.fsync(stream.fileno())
        os.replace(name, path)
    finally:
        if os.path.exists(name):
            os.unlink(name)
```

临时文件放在目标目录，写完再通过 os.replace 替换。观察器的写入入口还有文件锁，用来避免两个观察进程同时更新同一份交接。自动生成的文件交给这个生成器维护，人工判断写进 notes 或 decisions，免得下次生成时被覆盖。

不过，state.json 和 HANDOFF.md 是分别替换的，中间可能发生中断。单个文件的原子替换没有让两份文件变成一个事务。恢复任务时仍要核对观察时间；摘要和状态不一致，就回到同次观察记录确认。这里还有改进空间。

## 新会话沿哪条路径接手

恢复任务时，先确认项目和当前问题，沿已有入口找到交接，再读下一步依赖的材料。详细历史只在需要解释某个决定时检索。比如想知道一个采样方案为什么放弃，就找当时的实验和判断；修一个明确的 UI 问题，通常不需要这些研究记录。

交接至少要能回答：目标是什么，当前到了哪个阶段，最近查到了什么，缺什么，下一步做什么，怎样验收。重要结论旁边附上核验时间和原件入口。

“训练正常”就写得太宽了。进程还在、epoch 增加、评估通过，分别支持不同的判断。观察器会比较阶段、轮数、checkpoint 和任务计数；如果没有可测的进展，会留下提示。关键输入缺失或 JSON 只写了一部分时，状态会标成 unverified。

它的输出还明确保留了这两个字段：

```python
'scientific_acceptance': 'not_assessed_by_observer',
'visual_acceptance': 'not_assessed_by_observer',
```

观察器能报告读到的运行状态。论文结论是否成立、图能不能交付，需要另外检查。我不希望下一次接手看到“进程运行中”，就把评估和逐图检查一起略过了。

入口文件存在，也不能据此认定新会话已经读过正确内容。实际接手时要核对它找到了哪项任务、使用了哪份结果。通过本地会话操作远端项目时，还要读取远端规则，不能拿本地入口替代。

## 嵌套目录带来的归属问题

整理时发现过一次误归属：外层工作台下面放着 Hermes，之前却把 Hermes 里的上下文目录当成了外层项目的通用工作区。

文件能写进去，所以问题不会在写入时暴露。以后从外层项目恢复任务，交接却放在另一个独立项目里；Hermes 自己的记录也会混入外层内容。后来把外层交接放回外层项目，让 Hermes 保留自己的入口。

因此，总索引记录项目边界和入口，不镜像各项目实时进度。碰到嵌套仓库，先确认实际项目根，再决定文件归属。参考代码也要保留原作者归属，不能因为它放在我的工作区里，就当成我的实现。

恢复备份时还有另一个版本问题。备份后的文件可能被继续修改，直接覆盖会丢掉后来的工作。现有迁移记录保存了改造后的校验值，恢复前可以先比较；当前版本已经变化，就需要合并。

## Skills 放重复步骤

Skills 保存重复会用到的操作说明，任务交接保存这次做到哪里。步骤适用范围、输入输出和检查方法可以复用，某次实验的进度留在所属项目。

上下文初始化也有一个 Skill，但适用范围后来收窄为新项目，或已有入口缺失、失效时的修复。README、交接或状态生成器已经能找到任务，就继续用它们。这也避免了每次接手都再造一份“当前状态”。

不同项目需要的步骤差别很大。Notebook 修改、数据下载和服务排障可以有各自的说明，不必套进一个通用的长流程。目录按实际任务增长，空目录先不建。

## 维护交接的成本

这次改造检查了文件、入口、备份和修改范围，没有做受控实验来比较任务成功率或接手耗时。现在能确认的是文件怎样组织、由谁更新；使用效果还要从实际接手中判断。

交接过期仍然会误导。观察器配置启用，也需要另查它是否触发、是否读到有效状态。旧快照可以帮助找线索，下一步依赖的运行状态仍要重新核对。

我目前继续沿用这些文件，修改重点是让每个结论的来源、时间和未解决的问题更容易找到。新增一份说明前，先看看有没有文件已经承担这个用途。否则过一阵子，还要先判断两份“当前交接”哪份算数。
