换一个对话继续做项目，我希望 Codex 先弄清两件事：这个项目有哪些约定，现在要接着做什么。前者可以放进 AGENTS.md，后者需要一份随工作更新的交接。

这套做法是我和 Codex 在几个项目里反复调整出来的。我提出要求、检查修改范围，Codex 协助整理文件。现在我更关心一条规则能不能让下一步明确，而不是管理目录看起来有多完整。

## AGENTS.md 里写什么

我会把需要长期遵守、又容易做错的事情留在这里。比如文件往哪里放，恢复旧任务先看哪里，做到什么程度要更新交接。

“保持项目整洁”很难落实。写成“新增文件前，先检查现有项目目录是否已有合适位置”，就能在建文件时用上。我的项目入口里保留了下面几条约定，这里缩短了原文：

- 新文件沿用所属项目或任务目录，已有位置能用就继续用。
- 恢复旧任务、切换主线或缺少背景时，按需读上下文入口；范围明确的小修改直接看相关文件。
- 有实质进展时更新已有交接，写清核验时间、阻塞和下一步。

这些条文都有一个触发条件。Agent 在准备建文件、接手任务或完成一段工作时，能知道该做什么。至于某次实验正在跑哪个版本、昨天卡在哪里，我放在任务交接里；否则每次进度变化都得修改项目规则。

如果你准备写自己的 AGENTS.md，可以先挑一条最近反复纠正过的问题，把“什么时候、做什么”写清楚，再慢慢补。起手就写一份包办所有事情的长文，后面很难维护。

## 进度放在交接里

项目进行久了，旧方案也会积累。换一个对话时，最需要的是知道当前采用哪个方案、下一步看哪个结果。完整历史可以等到有疑问时再查。

我给这些文件分了工：

| 文件 | 留下什么 |
| --- | --- |
| AGENTS.md | 项目长期约定，以及何时读取专门说明 |
| README 或上下文入口 | 当前任务的入口，相关文件在哪里 |
| HANDOFF.md | 当前目标、已完成到哪一步、卡在哪里、下一步和验收条件 |

交接里会链接原来的代码、Notebook 和结果，不把它们复制到管理目录。这样继续工作时，仍然查看正在维护的原件。

一句“实验完成”也不够。训练跑完了，评估可能还没做；图导出了，也可能还没检查。交接应写出实际完成的部分，把没核实的内容留着。接手的人才能决定先看结果，还是先补检查。

## 按任务决定读多少

我在 AIQuant 的根规则里保留了 Notebook 和清理工作的入口，把专门细则放进单独文档。需要创建、修改或执行 Notebook 时再打开对应说明；清理数据和报告时，读清理规则。

这样根文件负责指路。假如只是改一个按钮的文案，就从那个组件开始；恢复一项搁置的研究，再沿入口找到交接和相关实验。两个任务需要的背景本来就不同。

这也意味着我不会只看见文件存在，就认定 Codex 已经理解了项目。接手后还要看它找到了哪个任务、准备使用哪个结果。远程工作时，我会让它读取远端项目自己的规则，不能用本地说明代替。

## 目录先分清是谁的

整理工作区时，外层项目的一份上下文目录曾经放进嵌套的 Hermes 项目。文件能写进去，链接也能打开，但恢复外层任务时，入口却落在另一个独立项目里。

后来把外层交接移回它自己的目录，Hermes 保留自己的入口。这个例子让我检查目录时会多看一层：它属于同一个项目，还是碰巧放在这个文件夹下面？

总索引因此只负责指向各项目入口。当前进度由各项目自己维护，避免两处各写一份，时间久了对不上。

## 小项目可以少几份文件

已有 README 和一页交接能找到工作，就继续用。多项长期任务确实需要分别维护时，再增加任务目录。决定记录、事件日志也按实际需要增加，不预先摆一排空文件。

重复使用的操作方法可以整理成 Skill，任务交接只链接它。比如某一步下载受阻，交接留下当前缺了什么、下一步怎么处理；通用的下载检查方法由 Skill 维护。我的上下文初始化 Skill 也收缩到新项目或入口缺失、失效的情况，普通接手沿用已有文件。

我还没有做过交接耗时或任务成功率的对照实验。这篇记录的是目前采用的组织方法。接下来继续维护时，我会先检查交接是否过时：下一步变了就更新，旧结论留下来源；执行要依赖的运行状态，再查一次。
